# Agent、工具与上下文工程

> **更新时间**：2026-07-29
>
> **事实审校**：Agent 架构、工具协议、短期/长期记忆、安全边界与轨迹评测已按官方文档和原始论文复核；产品接口以本次更新时间为边界。

前面的章节解释了模型如何训练、如何推理、如何部署。到了真实应用层，开发者面对的往往不只是“调用一次模型”。一个可用的 AI 系统需要理解任务、读取上下文、调用工具、保存中间状态、处理失败、向用户交付结果。这类系统通常被称为 agent。

Agent 不是一种新模型，是一种把模型放进工作流里的系统架构。模型负责理解、推理和生成，系统负责提供上下文、限制权限、执行工具、记录状态和校验结果。理解 agent，不要把它想象成”更聪明的聊天机器人”，它就是一个围绕大模型构建的闭环执行系统。

## Agent 的基本结构

用户说“修复失败的测试”时，系统不能只生成一段修改建议：它要读取报错、定位代码、编辑文件、运行测试，并根据新结果继续。一次模型调用无法独立完成这个跨步骤闭环，因此需要把目标、上下文、工具和循环组合起来。

一个最小 agent 通常包含四个部分：目标、上下文、工具和控制循环。

目标来自用户或上游系统。例如“修复这个测试失败”“根据设计稿生成页面”“分析本周用户流失原因”。目标越清晰，agent 越容易判断下一步应该做什么。

上下文是 agent 做决策所需的信息。它可以来自当前对话、代码文件、数据库、日志、设计文档、历史记忆或外部服务。模型本身不会自动知道项目事实，必须通过上下文把事实放到它能使用的位置。

工具是 agent 改变外部世界的方式。读文件、写文件、执行 shell 命令、查询数据库、调用搜索、创建工单、发起部署，都属于工具调用。没有工具，模型只能给建议；有了工具，agent 才能实际完成任务。

控制循环决定 agent 如何反复行动。典型流程是：观察当前状态，规划下一步，调用工具，读取结果，更新判断，再继续下一步。这个循环可以很短，例如只调用一次检索；也可以很长，例如跨多个文件修复 bug、运行测试、继续修改直到通过。

可以把 agent 写成下面的抽象流程：

```text
while task_not_done:
  context = gather_context(goal, memory, environment)
  action = model_decide(goal, context, available_tools)
  result = execute_tool(action)
  record(result)
  if need_user_confirmation:
    ask_user()
```

这段伪代码很简单，困难全在工程细节：哪些上下文应该放进模型，哪些工具可以自动执行，哪些操作必须让用户确认，工具失败后如何恢复，任务是否已经完成，怎样避免无限循环。

如果用更接近代码的形式，一个最小 agent 循环可以写成这样：

```python
while not done:
    context = collect_context(goal, memory, tool_results)
    action = call_model(goal, context, tools)

    if action.type == "final_answer":
        done = True
        answer = action.content
    elif action.type == "tool_call":
        result = run_tool(action.name, action.arguments)
        tool_results.append(result)
    else:
        raise ValueError("unknown action")
```

工具调用接口的具体字段会随平台变化，但完整生命周期不应只停在“模型提出调用”。下面的厂商中立伪代码把模型、策略和工具执行分开：

```python
while run.status == "running":
    prompt = context_builder.compile(run)
    action = model.generate(prompt, tools=tool_registry.schemas())

    if action.type == "final_answer":
        verification = verifier.check(action.content, run)
        run.finish(action.content) if verification.ok else run.replan(verification)
        continue

    call = tool_registry.parse_and_validate(action.tool_call)
    decision = policy.authorize(
        identity=run.identity,
        goal=run.goal,
        tool=call.name,
        arguments=call.arguments,
    )

    if decision.requires_approval:
        run.pause("waiting_for_approval", pending_call=call)
        checkpoint_store.save(run)
        return

    result = tool_executor.invoke(
        call,
        capability=decision.capability,
        idempotency_key=call.call_id,
        timeout=decision.timeout,
    )
    run.append_tool_result(call.call_id, result)
    checkpoint_store.save(run)
```

模型只提出动作；参数解析、鉴权、审批、副作用执行和状态持久化都由模型外代码完成。工具结果还要带着 `call_id` 回到同一次运行，模型才能基于真实结果继续，而不是假设动作已经成功。

真实系统会比这复杂得多：要处理权限、重试、超时、预算、并发、日志、验证和人工确认。但这个循环说明了 agent 的核心：模型不是一次性回答，是在系统提供的环境里反复观察和行动。

看一个具体过程。用户说：“帮我修复 `src/utils.ts` 里的类型错误。”

第一轮，agent 先读取错误日志和 `src/utils.ts`，判断类型错误来自哪个函数。第二轮，它修改类型定义或调用方式。第三轮，它运行类型检查，发现还有一个关联文件报错。第四轮，它继续读取关联文件，调整导出类型。第五轮，它再次运行类型检查，确认通过。第六轮，它查看 diff，向用户说明改了什么、验证了什么。

这个例子里，agent 不是一次生成完整答案，是在”观察 -> 行动 -> 验证 -> 再行动”的循环中推进。每一轮都依赖上一轮工具返回的事实。如果它误读了错误日志，后续步骤就会偏离；如果它不运行验证，就可能把看似合理但无法通过编译的代码交给用户。

## Agent Harness：把模型包进可控执行环境

最小循环在演示里能跑，进入生产后却会遇到进程重启、工具超时、人工审批、预算耗尽和重复扣款等问题。模型既不应负责保存权威状态，也不能仅凭一句“已经执行”证明副作用真的成功。系统需要一个模型之外的运行层来承接这些责任。

Agent harness 是模型之外的运行外壳。不同框架也会使用 runner、runtime、orchestrator 或 agent framework 等名称；这里把负责驱动循环、连接工具、保存状态和执行控制策略的系统层统称为 harness。模型负责提出判断和动作，harness 负责让这些动作在真实环境里可执行、可暂停、可追溯并受权限约束。

没有 harness，模型只是一个会给建议的对话组件——它可以告诉你”应该读取文件、修改代码、运行测试”，但不会自己管理这些步骤。有了 harness，系统才能把模型输出转成可执行动作，并把动作结果重新喂回模型，形成”观察 -> 行动 -> 反馈 -> 修正”的闭环。

### 控制面、执行面与状态面

可以把 harness 分成三个相互约束的平面：

```text
入口：用户 / API / 定时任务 / 事件
                    │
           ┌────────▼────────┐
控制面     │ 调度、循环、预算、策略、审批、停止条件 │
           └────────┬────────┘
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
上下文编译器     模型运行器      工具网关与沙箱       ← 执行面
       │            │            │
       └────────────┼────────────┘
                    ▼
运行状态 / 检查点 / Artifact / Trace / 记忆          ← 状态面
```

控制面决定现在能否继续、可以调用什么以及何时必须暂停。执行面负责组装模型输入和运行工具。状态面保存可恢复运行所需事实以及调试证据。把三者混在一个 prompt 或一个进程内存对象里，系统一旦重启、等待人工审批或并发执行，就很难保持一致。

一个 harness 通常负责这些工作：

- 任务管理：保存用户目标、当前进度、待办步骤和完成条件。
- 上下文管理：决定哪些指令、文件、记忆、检索结果和工具输出进入本轮模型上下文。
- 工具注册：告诉模型有哪些工具可用，每个工具需要什么参数，调用后会返回什么。
- 执行控制：解析模型提出的工具调用，执行工具，并把结果记录下来。
- 权限边界：区分只读、写入、网络请求、部署、删除等不同风险级别。
- 错误恢复：工具失败、参数错误、权限不足或测试不通过时，决定重试、换方案还是请求用户介入。
- 验证闭环：在修改代码、生成文件或调用业务系统后，运行测试、检查格式、校验结果。
- 观测与审计：记录模型输入、工具调用、输出结果、耗时、成本和失败原因。

它和 MCP、skills、记忆的关系：MCP 提供外部工具和资源，skills 提供某类任务的操作说明，记忆提供长期上下文，harness 负责把这些能力组织起来，决定什么时候取上下文、什么时候调用工具、什么时候执行 skill、什么时候要求用户确认。

Agent 的能力不只来自模型大小，也来自 harness 的工程质量。一个弱 harness 会让强模型也频繁误用工具、丢失状态或跳过验证；一个设计良好的 harness 可以让模型在明确边界内稳定执行任务，即使模型偶尔出错，也能通过权限、日志、验证和回退把风险控制住。

### 把一次运行建模为状态机

生产系统不应只用一个 `while True` 表示运行。一次 run 至少要区分正常结束、预期暂停和异常失败：

```text
queued → running ───────────────→ completed
            ├→ waiting_for_input ─┐
            ├→ waiting_for_approval│→ running
            ├→ retry_scheduled ────┘
            ├→ failed
            └→ cancelled
```

`waiting_for_approval` 不是失败，也不是开启一段全新对话。Harness 应保存原任务、待审批工具名、准确参数、调用 ID、权限决定和过期时间；用户批准后从同一个检查点继续。否则系统可能丢失此前工具结果、重复计算，甚至用审批旧参数的令牌执行新参数。

运行状态可以从下面的最小结构开始：

```yaml
run_id: run_01J...
status: waiting_for_approval
goal: 修复 src/utils.ts 的类型错误并通过类型检查
identity: { user_id: u-42, tenant_id: t-7 }
budget: { max_turns: 20, max_tool_calls: 40, deadline: 2026-07-28T16:00:00+08:00 }
cursor: step-6
pending_call:
  call_id: call-9
  tool: apply_patch
  arguments_hash: sha256:...
artifacts: [patch://run_01J/changes.diff, log://run_01J/typecheck-2]
versions:
  harness: 1.4.0
  prompt: coding-agent@12
  toolset: repo-tools@7
  model: model-family@snapshot
```

检查点应在可恢复边界写入，例如模型轮次结束、工具副作用提交、等待输入和任务结束时。除了消息历史，还要保存未完成调用、预算消耗、外部资源版本和配置版本。长期等待的任务恢复时，代码、prompt 或工具 schema 可能已经升级；没有版本信息，旧状态可能无法安全反序列化或会在新规则下产生不同副作用。

### 工具调用要按副作用事务处理

Harness 处理一次工具调用时，至少要经过：

```text
模型提出调用
→ schema 解析与类型校验
→ 按真实用户、租户、资源重新鉴权
→ 风险分类与必要审批
→ 生成幂等键并记录“准备执行”
→ 在受限环境中执行
→ 规范化成功、可重试错误和永久错误
→ 记录外部状态变化与 artifact
→ 把结果返回模型
```

读取文件和查询订单通常没有外部副作用；写文件、发邮件、付款和部署则改变外部世界。后者要考虑“工具已经成功，但响应在返回前超时”的情况。如果 harness 不保存幂等键，自动重试可能造成重复扣款或重复发送。并非所有失败都应重试：参数非法需要让模型修正，权限拒绝通常需要请求授权，限流可以指数退避，业务规则拒绝则应停止或转人工。

并行调用也需要明确语义。两个只读查询可以并发；两个修改同一文件或同一订单的调用可能互相覆盖。Harness 应记录资源版本、为冲突资源加锁或使用乐观并发控制，并在父任务取消时向子任务传播取消信号。到达 token、时间、费用或工具次数预算后，应进入可解释的停止状态，而不是继续无限循环。

### 区分上下文、运行状态、记忆、Artifact 与 Trace

这些对象都会“保存信息”，但用途不同：

| 对象 | 主要目的 | 生命周期 | 是否直接放进模型上下文 |
|---|---|---|---|
| 上下文 | 让模型完成当前一轮判断 | 一次模型调用 | 是，但受 token 预算限制 |
| 运行状态 | 让任务能暂停、恢复和并发控制 | 一次 run 或 thread | 按需编译少量字段 |
| 短期记忆 | 保持当前会话与任务连续性 | 一个 thread | 选择、裁剪或摘要后加入 |
| 长期记忆 | 跨会话复用事实、偏好和经验 | 跨 thread | 检索相关部分加入 |
| Artifact | 保存文件、补丁、报告和大型工具输出 | 由任务和保留策略决定 | 通常只放引用或摘要 |
| Trace | 调试、审计和评测执行过程 | 按审计策略保留 | 通常不直接加入 |

例如类型检查产生的 10 MB 日志应成为 artifact，运行状态只保存 URI、哈希和摘要，本轮上下文再选取与当前错误相关的几十行。把完整日志既塞进消息历史又写进长期记忆，不仅浪费上下文，还会把临时噪声带入未来任务。

### 用类型错误案例走完 Harness

前面的六轮例子如果放进 harness，会变成一条有状态的执行记录：

1. 创建 run，冻结用户目标、允许写入的目录和“类型检查通过”这一完成条件。
2. 在沙箱中读取错误日志与目标文件，把原始日志保存为 artifact，把相关行放入上下文。
3. 模型提出补丁；策略检查路径范围，工具使用文件版本或内容哈希避免覆盖并发修改。
4. 保存补丁和检查点，运行类型检查；失败结果绑定到工具调用并进入下一轮。
5. 若连续失败达到阈值，重新规划或暂停请求用户输入，而不是重复同一修改。
6. 验证通过后检查 diff、无关文件和用户已有改动；只有终态断言成立才标记 `completed`。

如果进程在第 4 步后崩溃，恢复时应从已保存的补丁和测试结果继续，而不是再次盲目修改；如果用户在等待审批时取消任务，待执行调用必须失效。可恢复、可取消、可验证，才是 harness 相比一段模型循环真正增加的工程价值。

## Loop Engineering：设计 Agent 的迭代闭环

把很多工具交给模型，并不代表任务会自然收敛。Agent 可能重复同一失败操作、修改后不验证、在两种方案间来回摆动，或在已经满足目标后仍继续行动。要让开放式任务可靠结束，需要专门设计每一轮怎样进入、验证、恢复和停止。

Loop engineering 是对 agent 执行循环的工程设计。它不关注单次 prompt 怎么写，关注的是 agent 如何在多轮过程中观察环境、决定下一步、调用工具、读取结果、验证输出、修正计划，并在合适的时候停止。

Prompt engineering 优化”这一轮模型该怎么回答”，loop engineering 关心”这个系统如何一轮接一轮地推进任务”。对 agent 来说，很多失败不是因为模型完全不会，而是循环设计有问题：没有明确停止条件、工具失败后反复重试、没有验证就宣布完成、越修越偏离目标，或者遇到高风险操作时没有请求用户确认。

一个典型 agent loop 可以写成：

```text
目标
  -> 获取上下文
  -> 规划下一步
  -> 调用工具
  -> 读取工具结果
  -> 验证结果
  -> 更新任务状态
  -> 判断继续、重试、换策略、请求确认或停止
```

这个循环里需要设计的不是一个点，是一组控制规则：

- 什么时候继续执行？
- 什么时候认为任务已经完成？
- 工具失败时是重试、换工具，还是请求用户介入？
- 验证失败时应该回滚、修复，还是缩小任务范围？
- 当前策略连续失败几次后，是否应该重新规划？
- 哪些操作可以自动执行，哪些必须让用户确认？
- 哪些中间结果应该写入任务状态或长期记忆？
- 如何限制循环次数、token 成本和工具调用成本？

Loop engineering 和 agent harness 的关系很紧密。Harness 是运行外壳，负责提供上下文、工具、权限、日志和验证能力；loop 是 harness 内部驱动 agent 前进的控制逻辑。没有 harness，loop 缺少执行环境；没有好的 loop，harness 只是把工具摆在那里，agent 仍然可能乱用。

以 coding agent 为例，一个好的 loop 不会在修改代码后直接说“完成”。它应该运行测试或类型检查，读取失败信息，判断错误是否由本次修改引起，再决定继续修复还是回退。如果连续几轮都在同一个错误上失败，它应该停止盲目尝试，向用户说明当前状态和可选方案。

以客服 agent 为例，一个好的 loop 不应在用户要求退款时直接调用退款工具。它应该先确认身份，查询订单状态，检查退款规则，判断是否需要人工介入，再在高风险操作前让用户确认。这里的 loop 设计决定了系统是“会说话的机器人”，还是“能安全执行业务流程的 agent”。

Loop engineering 也和近年的 environment engineering 相邻。Environment engineering 更强调通过环境、权限、预算、artifact 管理和人工介入机制来塑造 agent 行为；loop engineering 更聚焦执行循环本身：每轮如何进入、如何退出、如何验证、如何恢复。两者共同决定 agent 能否可靠运行。

## Agent 与普通工作流的区别

传统自动化工作流通常是确定的。开发者提前写好步骤：第一步拉取数据，第二步转换格式，第三步生成报表。输入变化不能太大，否则流程容易失败。

Agent 工作流更适合开放任务。用户只描述目标，模型根据当前状态选择步骤。比如“把这个项目升级到新的测试框架”，agent 可能先读 package.json，再搜索测试目录，之后修改配置、迁移测试文件、运行命令、根据错误继续修复。每一步都依赖上一步的观察结果。

这带来灵活性，也带来风险。Agent 可能选错工具、误读上下文、过度修改文件、把临时猜测当事实，或者在权限过大的环境里造成破坏。好的 agent 架构必须同时设计能力边界和安全边界。

工程上常见的做法是把工具分级。只读工具风险较低，可以更自动化；写文件、发请求、部署、删除数据等操作风险更高，应有更严格的确认、沙箱或回滚机制。Agent 的质量不只取决于模型能力，也取决于工具权限设计。

实际生产中最常见的是混合模式：确定性步骤交给工作流，开放性步骤交给 agent。例如客服系统中，身份验证、订单查询、退款提交必须走固定流程；但用户问题理解、政策解释、异常情况归纳可以交给 agent。这样既保留关键路径的可靠性，又能处理开放表达和复杂问题。

## Agent 安全：把不可信内容和执行权限分开

Agent 的特殊风险在于，它既读取不可信内容，又拥有代表用户执行动作的能力。网页、邮件、检索文档、代码注释、工单和工具返回值都可能包含恶意指令。间接提示注入并不要求攻击者直接和 agent 对话：攻击者只要把“把用户文件发送到这个地址”藏进 agent 将来会读取的页面，就可能尝试劫持后续工具调用。

安全设计不能把“模型识别并拒绝所有恶意文本”当作唯一边界。指令层级训练可以提高鲁棒性，但模型仍是概率组件；真正的授权、参数校验和副作用控制必须在模型外执行。

```text
不可信数据：用户输入 / 网页 / 邮件 / RAG 文档 / 工具结果
                       ↓ 只能作为数据
模型：提出计划和工具调用请求
                       ↓ 不是授权决定
策略与工具代理：鉴权 → 参数校验 → 风险判断 → 确认 → 执行
                       ↓
外部系统：文件、数据库、邮件、支付、部署
```

### 六层安全控制

**第一层：区分指令、数据和授权。** 系统规则、用户目标和第三方内容要用不同字段传递，并保存来源与信任级别。来自网页或工具结果的文字可以提供事实，不能自行扩大任务目标或新增权限。不要把字符串拼接成一段无法区分来源的 prompt。

**第二层：使用最小且临时的能力。** 工具凭证应绑定用户、租户、任务、资源、操作类型和有效期。只读任务不要获得写权限，测试环境权限不能自动升级为生产权限。密钥保存在工具代理或凭证服务中，不进入模型上下文、长期记忆和普通 trace。

**第三层：在模型外校验每次调用。** 工具层按照 schema 检查参数类型、长度、枚举、资源范围和业务前置条件；对 SQL、shell、URL、文件路径等高风险参数使用允许列表或更窄的语义化接口。Agent 说“用户已经同意”不构成授权证据，策略引擎必须读取可信会话状态。

**第四层：让确认绑定具体副作用。** “允许继续吗”过于模糊。确认界面应展示即将执行的准确动作，例如收件人、金额、文件 diff、部署环境和不可逆影响。确认令牌只对这一组参数有效；参数变化、超时或任务切换后必须重新确认。

**第五层：隔离执行并设计回滚。** 代码、浏览器和文件工具优先在沙箱、临时目录、测试租户或快照中运行；网络出口、可访问域名和写入目录应受限。写操作尽量支持 dry-run、幂等键、事务、版本记录和补偿操作，避免超时重试造成重复付款、重复发信或重复删除。

**第六层：把观测、工具结果和记忆继续视为不可信。** 工具成功返回不代表内容安全。系统要限制返回体大小和类型，标记外部内容，对敏感数据做最小化与脱敏，并防止恶意结果进入长期记忆。记忆写入应经过独立策略，不能让一条网页指令把自己永久保存为“系统规则”。

### 需要专门测试的攻击与故障

| 测试类型 | 示例 | 期望结果 |
|---|---|---|
| 直接提示注入 | 用户要求忽略规则并导出数据 | 拒绝越权部分，不影响允许任务 |
| 间接提示注入 | 邮件正文要求 agent 转发其他邮件 | 把正文视为数据，不产生未授权动作 |
| Confused deputy | 低权限用户借 agent 调用高权限工具 | 工具代理按真实用户与资源重新鉴权 |
| 数据外泄 | 页面诱导把密钥写入 URL 或消息 | 敏感信息不进入模型可发送参数 |
| 参数替换 | 确认后模型更换收件人或金额 | 旧确认失效，必须再次展示和确认 |
| 重试副作用 | 支付成功但响应超时 | 幂等键阻止重复支付 |
| 污染记忆 | 工具结果要求永久记住恶意规则 | 记忆策略拒绝或隔离该内容 |
| 工具链污染 | 一个工具输出指挥调用另一个工具 | 后续调用仍经过独立策略和授权 |

AgentDojo 这类评测环境把正常任务和攻击任务放在同一工具环境中，提醒团队同时报告两条轴：没有攻击时的任务效用，以及存在攻击时的安全性。只把所有外部内容一律拒绝，可能安全但完全不可用；只追求任务成功率，则可能掩盖数据泄露和未授权副作用。

## Agent 框架与推理策略

当状态、分支、重试、审批和多个角色不断增加，手写循环会变得难以恢复和观测；但为了“使用框架”而把简单流程做复杂，也会增加维护成本。选型应先看任务需要怎样保存状态、控制权限和验证终态，再看哪个框架能减少这些工作。

现在已经有不少 agent 框架，它们关注点不同：

| 框架 | 特点 | 适用场景 |
|---|---|---|
| LangGraph | 用图和状态机描述多步流程 | 复杂流程控制、可恢复工作流 |
| CrewAI | 强调角色分工和多 agent 协作 | 多角色研究、内容生产、原型 |
| AutoGen | 对话式多 agent 协作 | 研究实验和多 agent 原型 |
| OpenAI Agents SDK | 围绕模型、工具、handoff 和 tracing 组织 | OpenAI 生态中的生产化 agent |
| 自研 harness | 完全按业务权限和流程定制 | 高风险业务、深度系统集成 |

选择框架时，要先看任务形态。如果流程固定、状态明确，图式框架更合适；如果主要是工具调用和少量分支，轻量 harness 可能足够；如果涉及生产权限、审计和合规，自研控制层往往不可避免。

Agent 的智能不只来自工具数量，也来自推理策略。ReAct 把推理和行动交替组织：先说明下一步想做什么，再调用工具，再根据观察继续。Reflexion 强调失败后的自我反思，把错误原因写回上下文，帮助下一轮改进。Tree-of-Thought 会探索多条思路，再选择更有希望的路径。这些策略不保证一定更好，但它们说明：agent 不是单次 prompt，是一个可以设计搜索、反思和验证过程的系统。

## MCP：把外部能力标准化

当每个 AI 客户端都要分别适配 GitHub、数据库、设计工具和工单系统时，客户端数量乘以服务数量会迅速变成大量重复集成；工具描述、鉴权和结果格式也各不相同。需要一种通用连接协议，让能力可以被多个客户端发现和复用。

MCP 是 Model Context Protocol 的缩写。它是一个开放协议，用来标准化 AI 应用和外部系统之间的连接方式。MCP 类似 agent 世界里的”通用接口”：不同工具、数据源和服务不需要为每个 AI 客户端单独开发一套集成，只要按 MCP 暴露能力，支持 MCP 的客户端就可以发现和调用它们。

需要注意，MCP 是 Anthropic 提出的开放协议，并不是唯一的工具接入方式。OpenAI 有 function calling 和工具调用接口，其他平台也有自己的插件或扩展机制。MCP 的优势在于开放和复用：同一个 MCP server 可以被多个支持 MCP 的客户端使用，而不必为每个客户端单独开发一套集成。

MCP 的价值在于解耦。客户端负责和模型交互、展示界面、管理权限；MCP server 负责把某个外部系统的能力包装出来。例如一个 GitHub MCP server 可以暴露查询 issue、读取 PR、创建评论等工具；一个数据库 MCP server 可以暴露受控 SQL 查询；一个 Figma MCP server 可以暴露设计稿读取能力。

MCP 中常见的能力包括 tools、resources 和 prompts。

Tools 表示可执行动作。调用工具会产生结果，也可能改变外部状态。比如 `search_issues`、`run_query`、`create_ticket`、`send_message`。工具通常有参数 schema，让模型知道应该传什么字段，也让系统可以校验输入。

一个简化的 MCP 工具定义可以像这样：

```yaml
name: search_orders
description: 按订单号查询订单状态，只返回当前用户有权限查看的订单
input_schema:
  type: object
  properties:
    order_id:
      type: string
      description: 订单号
  required:
    - order_id
permissions:
  risk: read_only
  requires_user_identity: true
```

关键不在 YAML 语法本身，而在于工具的语义、参数和权限边界是否足够清楚。模型看到 `search_orders`，比看到一个任意 SQL 查询工具更容易正确使用；系统也更容易校验用户身份、限制返回字段和记录审计日志。

Resources 表示可读取的上下文。它们更像文件、文档、记录或数据对象。Agent 可以读取资源，把相关内容放进模型上下文。Resources 的重点是“提供事实”，而不是“执行动作”。

Prompts 表示可复用的提示模板。MCP server 可以把特定工作流包装成 prompt，例如”代码审查模板””生成周报模板””排查告警模板”。用户或客户端显式选择后，agent 按模板组织任务。

设计 MCP server 时，最重要的问题不是”能暴露多少功能”，而是”暴露什么抽象”。一个好的工具应该接近业务意图，不是把底层 API 原样丢给模型。例如 `refund_order(orderId, reason)` 通常比一组零散的 HTTP 请求工具更安全、更容易使用，也更容易做权限控制和审计。

MCP 不等于无限信任外部工具。Server 返回的内容可能过大、过期、错误，甚至包含提示注入。客户端需要做权限隔离、结果裁剪、来源标注和用户确认。对高风险操作，agent 应该先解释计划，再请求授权，而不是直接执行。

## Skills：把重复能力打包

工具只告诉 agent“能够做什么”，却不告诉它团队要求“应该按什么顺序做、什么算通过、哪些操作禁止”。没有可复用说明，同类任务每次都要重新摸索，执行结果会因上下文和模型选择而不一致。

Skills 是给 agent 使用的任务说明包。它通常包含触发条件、操作流程、领域知识、约束、示例，必要时还会附带脚本、模板和参考文件。模型在遇到匹配任务时读取 skill，按照其中的方法完成工作。

Skills 和 MCP 解决的是不同问题。MCP 主要解决“连接什么外部能力”，skills 主要解决“面对某类任务应该怎么做”。前者像接口和工具箱，后者像操作手册和专业训练。

例如一个“图片优化”skill 可以告诉 agent 如何扫描图片尺寸、判断是否需要降采样、生成压缩建议。一个“MCP server 开发”skill 可以告诉 agent 如何选择传输方式、如何设计工具 schema、如何写鉴权和测试。一个“发布检查”skill 可以规定发布前必须跑哪些命令、检查哪些配置、生成什么格式的 release note。

好的 skill 应该足够具体。只写”请认真检查代码”没有价值，模型本来就知道要认真。更有用的是写清楚检查顺序、通过标准、常见陷阱、可复用命令和输出格式。

Skills 也要控制粒度。粒度太大，会变成一本模糊手册，模型难以在具体任务中执行；粒度太小，会产生大量碎片，调度成本变高。通常适合把 skill 设计成围绕一个稳定任务闭环，例如“创建一个插件”“分析一组贴图是否可以缩小”“为一个服务添加 OpenAPI 文档”。

一个简化的 code review skill 可以写成这样：

```yaml
name: code-review
trigger: 用户请求代码审查
steps:
  - 读取变更文件和相关上下文
  - 检查潜在 bug、边界条件和行为回归
  - 检查安全问题和权限风险
  - 检查是否缺少必要测试
  - 按严重程度输出发现
constraints:
  - 默认只审查，不直接修改
  - 每个发现需要指向具体文件和代码位置
  - 不把风格偏好当成严重问题
```

这样的 skill 不是给模型”知识百科”，是把稳定工作流程变成可复用操作说明。

## 记忆：让 agent 跨会话积累上下文

大模型调用本身通常是无状态的。一次请求结束后，模型不会天然记住项目偏好、构建命令、用户习惯或上次排查结论。所谓记忆，是 agent 系统在模型外部保存信息，并在后续任务中重新取出使用。

不要把模型权重中的知识、当前 prompt、聊天记录、数据库和向量索引全都叫作同一种记忆。对应用工程最有用的是两个正交维度：记忆持续多久，以及记忆保存什么。

| 维度 | 分类 | 例子 |
|---|---|---|
| 生命周期 | 短期：一个 thread 或 run 内 | 消息、当前计划、工具结果、待审批调用 |
| 生命周期 | 长期：跨 thread 持久存在 | 用户偏好、项目事实、历史解决方案 |
| 内容类型 | 语义记忆：事实和概念 | “该仓库使用 npm run check” |
| 内容类型 | 情景记忆：发生过的经历 | “上次升级依赖时锁文件冲突，最后通过重建解决” |
| 内容类型 | 程序性记忆：如何完成任务 | 发布检查清单、代码审查 skill |

“短期/长期”回答保存多久，“语义/情景/程序性”回答保存什么。一个当前任务中的事实可以先进入短期记忆，经过验证和整理后再成为长期语义记忆；一段完整工具轨迹可以在任务内保留，任务结束后只提炼出可复用的情景或规则。

### 短期记忆：维护一个任务的工作状态

短期记忆也可称为 thread-scoped memory 或 working state。它通常包含：

- 用户消息和模型已经对用户公开的回复。
- 当前目标、计划、完成条件、预算和停止原因。
- 工具调用、结构化结果、错误和重试关系。
- 待确认问题、待审批副作用和用户决定。
- 临时推导、候选方案，以及 artifact 的 URI 和摘要。

短期不等于“只存在进程内存”。任务可能等待用户数小时，也可能在服务重启后继续，因此短期记忆应随 run 状态写入 checkpoint。它的“短”指作用域局限于当前 thread，而不是不能持久化。

对话增长后，不能无限把全部历史放进模型。常见管理策略如下：

| 策略 | 做法 | 风险与适用边界 |
|---|---|---|
| 保留最近窗口 | 原样保留最近若干轮 | 简单，但较早约束可能丢失 |
| 选择性保留 | 固定保留目标、用户决定、未完成事项和关键工具结果 | 需要定义重要字段和依赖关系 |
| 滚动摘要 | 把较早历史压成结构化摘要 | 摘要可能遗漏、误写或不断漂移 |
| 外部化 | 大日志、文件和报告存为 artifact，上下文只放引用 | 工具需要能按 URI 重新读取原文 |
| 按需重建 | 从事件日志、数据库和源文件重新编译当前上下文 | 更可靠，但增加读取与编排成本 |

摘要不应覆盖原始事实。可以把摘要保存成派生视图，同时保留消息 ID、工具调用 ID 和 artifact 哈希；关键决策需要时回到原记录验证。只对摘要反复再摘要，会让小错误逐轮积累。系统规则、用户刚刚确认的参数和未完成副作用也不应因为“太早”而被普通滑动窗口删除。

一份短期状态可以写成：

```yaml
thread_id: thread-87
run_id: run-142
goal: 将项目升级到新的测试框架并保持全部测试通过
status: running
decisions:
  - id: decision-3
    text: 用户要求保留现有快照测试
    source_message: msg-18
open_items:
  - 迁移剩余两个测试文件
pending_approvals: []
artifacts:
  - uri: log://run-142/test-4
    sha256: 4c1...
    summary: 42 个测试通过，2 个快照路径失败
```

### 长期记忆：保存跨会话仍然有用的信息

长期记忆的价值不是让 agent “什么都记得”，而是减少重复确认，并让稳定事实和可复用经验跨会话可见。长期内容通常分三类：

**语义记忆**保存事实、偏好和约定。例如用户希望中文回答、项目的构建命令、服务负责团队。事实需要来源、适用范围和有效时间。用户明确说“以后不要自动提交代码”，其优先级通常高于系统从历史行为推测出的偏好。

**情景记忆**保存具有结果的经历，例如某次故障的症状、采取的步骤和最终结果。原始 trace 往往太长，不适合直接作为长期记忆；更合适的是提炼成带证据引用的案例，并注明它只是一段历史经验，不保证适用于当前版本。

**程序性记忆**保存工作方法，例如发布清单、代码审查步骤和数据分析模板。生产系统中，重要流程更适合由开发者审核后放进版本化的 prompt、policy、skill 或代码，而不是让 agent 根据一次成功经历悄悄改写自己的核心规则。

作用域与内容类型是另一组独立属性：

- 用户作用域：只属于一个用户的偏好和事实。
- 项目作用域：仓库架构、命令和约定。
- 团队或租户作用域：组织内部共享知识，需权限控制。
- Agent 作用域：某个 agent 可复用的策略或案例。
- 全局作用域：通常只读的产品规则，不应由普通会话写入。

默认使用最窄作用域。把一位用户的偏好写成全局规则，或者让不同租户共享情景记忆，会造成错误个性化和数据泄露。

### 设计长期记忆的数据结构

一条可治理的记忆不应只有一段文字和一个 embedding。它至少需要身份、来源、作用域和生命周期：

```yaml
memory_id: mem-01J...
type: semantic
namespace: [tenant-7, project-book-cli]
subject: build-command
content: 本项目使用 npm run check 做基础语法检查
source:
  kind: repository
  uri: package.json
  revision: 73b03d1
confidence: verified
created_at: 2026-07-28T14:30:00+08:00
valid_from: 2026-07-13
expires_at: null
status: active
sensitivity: internal
acl: [book-cli-maintainers]
embedding_version: text-embedding@3
```

`content` 是给检索和模型使用的内容，`source` 是重新验证的依据，`namespace` 与 `acl` 决定谁能读取，时间字段说明何时有效，`status` 支持 superseded 或 deleted，embedding 只是派生索引版本。结构化事实还可以把规范化字段单独保存，例如语言偏好使用枚举，而不是依赖模型从自由文本解释。

长期记忆的事实源可以放在关系数据库或文档存储中，向量数据库作为语义检索索引。不要让向量索引成为唯一真相源：索引可能延迟、重建或使用有损 ANN，精确更新、删除、权限和审计通常还需要主存储。访问令牌、密码和不必要的个人敏感信息不应进入模型可检索的记忆。

### 记忆写入：先生成候选，再决定是否保存

让模型在任何时候随意写“我学到了……”会迅速产生重复、矛盾和被提示注入污染的记忆。更稳妥的写入链路是：

```text
对话、工具结果或任务总结
→ 提取候选记忆
→ 检查是否值得长期保存
→ 校验来源、身份、作用域和敏感性
→ 去重并查找冲突
→ 新增、合并、替代或拒绝
→ 写主存储与审计日志
→ 异步更新关键词/向量索引
```

“值得保存”通常意味着信息在未来仍可能复用、相对稳定、来源可追溯，并且用户允许保存。一次网络超时、模型的临时猜测和网页中的指令通常不值得进入长期记忆。用户明确确认的偏好、仓库中的真实命令和经过验证的故障结论更适合保存。

写入可以发生在热路径，也可以后台整理。热路径写入能立即影响下一轮，但增加延迟，并可能在事实尚未确认时过早固化；后台 consolidation 可以在任务结束后去重、归纳和校验，更适合情景记忆。高风险记忆可以先进入 `pending`，经过用户或规则确认后再激活。

冲突不能靠“最后写入覆盖一切”。系统要区分：

- 用户明确纠正：新记录替代旧偏好，并保留审计关系。
- 带时间的事实变化：给旧记录设置 `valid_to`，新旧都保留版本。
- 来源互相矛盾：按权威级别处理或标记冲突，等待确认。
- 模型推断与可信来源冲突：可信来源优先，推断不得覆盖。

时间衰减适合排序近期经历或可能变化的偏好，不适合自动降低安全政策和经过验证的长期事实。对不同记忆类型要使用不同更新语义，而不是一个统一“遗忘分数”。

### 记忆读取：先限制范围，再计算相关性

读取链路和 RAG 相似，但第一步不是向量搜索，而是确定可信身份和命名空间：

```text
当前用户、租户、项目和任务
→ ACL、有效时间、状态和敏感级别过滤
→ 关键词与向量召回
→ 去重、冲突处理与重排
→ 按 token 预算选择
→ 带来源、时间和信任级别注入上下文
```

可以综合相关性、时效性、重要性和来源可信度排序，但各信号的权重必须由任务评测决定。精确偏好、项目 ID 和当前版本适合结构化查询；模糊的历史案例适合语义检索；程序性记忆适合按触发条件加载 skill。不是所有内容都需要 embedding。

检索结果进入 prompt 时要清楚标注“这是可核查事实”“这是历史案例”还是“这是用户偏好”。历史上成功过的步骤不能伪装成当前环境事实。对高影响动作，agent 应重新读取权威系统，而不是仅凭记忆中的订单状态或权限判断执行。

### 删除、过期和用户控制

记忆系统必须从一开始就设计查看、纠正、删除和导出能力。删除不仅是删主表，还要处理向量索引、全文索引、缓存、派生摘要和备份保留策略。可使用 tombstone 防止异步索引把已删除记录重新写回，但 tombstone 本身也要有受控生命周期。

每类记忆应有保留策略：任务草稿可以短期过期，用户偏好保留到用户修改或删除，项目事实在来源版本变化时重新验证，安全审计日志按独立合规策略保存。记忆被用于哪次模型调用也应可追踪，这样发现错误记录时才能定位受影响的回答和动作。

### 评估记忆系统

只测试“模型能否想起用户名字”远远不够。记忆评测至少覆盖：

- 相关记忆能否在需要时被召回，非相关记忆是否被抑制。
- 用户纠正后旧记录是否停止生效，版本变化后能否重新验证。
- 摘要和 consolidation 是否保持原意与来源。
- 无权用户是否无法检索、推断或通过模型输出看到记忆。
- 恶意网页、邮件和工具输出是否会污染长期记忆。
- 删除后主存储、索引和缓存是否都不可再检索。
- 引入记忆后任务成功率是否提高，同时没有显著增加错误个性化和 token 成本。

记忆与 RAG 可以共用切块、embedding、混合检索和重排技术，但治理目标不同。RAG 主要从外部知识源为当前问题找证据；Agent 记忆还要决定哪些经历值得写入、属于谁、何时失效以及如何被纠正。好的记忆系统不是保存最多，而是在正确作用域内保存少量可验证、可更新、可删除的信息。

## 主流 AI 编程产品：不要只看模型名字

很多人知道 Codex、Claude Code、GitHub Copilot 和 Cursor 能写代码，却很难说清它们究竟有什么差异。一个常见原因是把模型、产品和使用界面混为一谈：模型负责生成与推理，coding agent 则在模型外面增加代码检索、文件编辑、终端、权限、状态、验证和协作机制。即使两个产品使用能力接近的模型，只要 harness 和交互表面不同，使用感受就可能明显不同。

可以把一款 AI 编程产品拆成六层来观察：

1. **模型层**：基础模型的代码能力、推理能力、上下文长度和响应风格。
2. **上下文层**：如何搜索文件、选择代码、读取项目说明、压缩历史，以及是否使用索引。
3. **循环层**：如何规划、执行、验证、重试、停止和请求用户介入。
4. **工具与权限层**：能否编辑文件、运行命令、访问网络、连接 MCP，以及哪些动作需要确认。
5. **隔离与并发层**：任务是在当前目录、沙箱、云环境还是 Git worktree 中运行，能否并行启动多个 agent。
6. **交付层**：结果以对话、编辑器 diff、提交、分支、issue 还是 pull request 的形式交给人审查。

因此，“哪个产品更聪明”通常不是一个足够好的问题。更有用的问题是：它如何取得上下文，默认怎样推进任务，在什么环境中执行，如何让人检查结果，以及这些选择是否适合当前工作。

### “实干者”和“规划者”：一个有用的使用模型

一种来自长期使用的直观感受是：**Codex 更像善于把目标拆成多个任务并推进实现的实干者；Claude Code 更像先理解全局、建立计划并寻找本质问题的规划者。** 这个比喻很有价值，因为它描述的不是聊天语气，而是用户在两种产品流程中最容易感知到的重心。

这种体验也有产品机制上的原因。Codex 的 CLI、IDE、桌面应用和云任务围绕可执行任务组织；桌面应用支持用 worktree 隔离多个任务，当前版本还把 subagent、多任务并行以及本地规划后交给云端继续实现作为显式工作流。一个主 agent 可以保留全局目标，把搜索、测试、审查或彼此独立的修改交给子 agent，最后汇总结果。对用户来说，“拆开、并行、完成并验证”的过程非常可见。

Claude Code 同样能读写文件、运行命令和完成实现，但它把“收集上下文 → 行动 → 验证”作为核心循环，并提供只研究和制定方案、不修改源码的 Plan mode。内置的 Explore、Plan 以及可自定义 subagent，可以先搜索代码结构、追踪调用链、读取日志和历史，再把较短的结论带回主上下文。官方文档中的修复流程也强调先定位根因再修改，因此用户很容易形成“它会先把事情想透”的印象。

不过，这个比喻不能被写成能力边界。Codex 也有 Plan mode、深度分析和代码审查；Claude Code 也能使用 subagent、后台任务和工具执行完整修改。最终表现还会被模型版本、入口、权限、项目规模、仓库说明、提示方式、时间预算和任务类型影响。更准确的说法是：**在特定版本和个人工作流下，两者的默认产品重心让人产生了不同体验，而不是一个只能执行、另一个只能规划。**

还要避免把“理解整个代码库”理解为一次性把所有文件塞进上下文窗口。真实产品通常会先查看目录和项目说明，再通过搜索、索引、语言服务或 subagent 选择相关文件，必要时摘要旧内容并回到原文核对。所谓全局理解，是多轮检索和推理形成的工作模型；代码库越大，项目边界、命名、测试和 `AGENTS.md`、`CLAUDE.md`、rules、`GEMINI.md` 等说明文件越重要。

### 主流产品放在同一张图里比较

下面比较的是截至 2026 年 7 月 28 日公开产品形态，不是永久排名。产品更新很快，实际使用前仍应检查当前文档、套餐、权限和数据策略。

| 产品 | 主要交互表面 | 容易被感知到的工作重心 |
|---|---|---|
| **OpenAI Codex** | CLI、IDE、桌面应用、云任务 | 拆分任务、subagent 并行、worktree 隔离和后台实现 |
| **Anthropic Claude Code** | 终端、IDE、桌面、Web | 代码库探索、Plan mode、根因分析和终端内持续调试 |
| **GitHub Copilot coding agent** | GitHub issue、Agents 页面、分支、PR | 把定义清楚的 issue 异步完成为可审查的 pull request |
| **Cursor Agent** | 编辑器侧栏、diff、checkpoint、远程后台任务 | 编辑器内即时迭代，以及离开编辑器后的后台分支实现 |
| **Gemini CLI／后续终端产品** | 开源终端入口、非交互运行、MCP、Web | 终端 harness、脚本与 CI 自动化、Google 生态集成 |

表中的“工作重心”不是能力清单。Codex 支持计划、skills、MCP 和自动化，但并行写同一批文件仍可能冲突，主 agent 必须负责依赖和集成验证。Claude Code 支持 `CLAUDE.md`、自动记忆、hooks、skills、MCP 和多类 subagent，但“善于全局分析”不等于一次读完仓库，长任务同样要控制上下文和协调成本。

GitHub Copilot coding agent 的优势是接入团队已有的 issue—branch—PR—review 流程，代价是它不像本地终端那样适合高频来回调试，环境准备、仓库权限、CI 和验收标准会直接影响结果。Cursor 的本地 agent 与远程 background agent 共享编辑器体验，但两种模式的网络、权限和数据边界不同；远程环境能访问互联网时，要谨慎管理密钥和不可信依赖。

Gemini CLI 的开源形态提供文件、shell、Web、MCP、checkpoint、`GEMINI.md`、非交互运行和规划能力，适合研究终端 agent 与自动化。Google 在 2026 年 6 月公告了个人用户终端入口向 Antigravity CLI 的迁移，因此产品名称、接入条件和可用入口必须以当前官方说明为准。

这张表还说明，产品边界正在变模糊。GitHub 不只是提供一个补全模型，也可以成为 coding agent 的任务与评审表面，并允许 Codex、Claude 等第三方 agent 进入相同的 issue—branch—PR 流程。Cursor 不只是编辑器内聊天，也提供远程后台 agent；Codex 和 Claude Code 也都横跨本地与云端。选型时应比较完整工作流，而不是只比较聊天窗口里的一次回答。

### 把“规划与执行”拆成可以测量的维度

如果只说一个产品“更会规划”，另一个“更会干活”，团队很难复现结论。可以把体验拆成下面几个维度：

| 维度 | 观察问题 |
|---|---|
| 探索与根因 | 是否找到关键入口、跨文件依赖和真正故障原因，还是只修改报错表面 |
| 计划质量 | 步骤是否有依赖顺序、风险、回滚方式和验收标准，遇到新证据是否修正计划 |
| 拆分与并行 | 能否识别真正独立的子任务，避免重复探索和多人同时修改同一文件 |
| 执行闭环 | 是否实际修改、运行测试、读取失败并继续修复，而不是只输出建议 |
| 变更质量 | diff 是否最小、符合架构约束、保留用户已有改动且没有无关重构 |
| 恢复能力 | 工具失败、测试不稳定、权限拒绝或上下文冲突后能否安全恢复 |
| 人机协作 | 需要多少次纠正，关键决策是否及时请求确认，最终结果是否易于审查和接管 |
| 成本与治理 | 完成时间、token/费用、数据边界、审计记录和高风险操作是否符合团队要求 |

比较产品时，可以固定同一个仓库 commit、运行环境、权限、模型档位、时间预算和验收测试，重复执行四类任务：根因不明显的 bug、跨模块重构、五个互不依赖的小任务，以及需要频繁看界面的交互修改。每次记录诊断准确率、测试通过率、无关 diff、人工介入次数、耗时、成本和安全违规。一次令人惊艳的演示只能证明“这一次成功了”，不能证明稳定优势。

### 按任务选择，也可以组合使用

如果问题边界模糊、故障横跨多个模块，可以先要求 agent 进入只读计划阶段：列出证据、未知项、根因假设和验证实验，确认后再授权修改。Claude Code 的 Plan mode 很适合显式表达这种流程，Codex 的 Plan mode 或独立探索 subagent 也能完成同类工作。

如果任务已经能拆成互不覆盖的实现单元，可以让主 agent 保留集成责任，把搜索、测试或各模块修改分给多个 subagent，并用 worktree 或独立分支隔离写入。Codex 的多任务表面让这类工作流更直观，但同样的原则也适用于其他支持后台 agent 的产品。

还可以采用混合工作流：先让一个产品输出带证据和验收标准的根因分析，再让另一个产品按里程碑实现；或者反过来，让执行 agent 先生成 patch，再让更擅长审查上下文的 agent 做独立 review。关键不是固定“Claude Code 负责想、Codex 负责做”，而是让计划、测试结果、diff 和审查意见都成为可传递、可验证的 artifact。只把一段聊天结论复制给另一个 agent，会丢失证据和环境状态。

最终，主流 AI 编程产品的真正差异不只在模型。它们是在选择不同的人机协作界面：终端强调紧密控制，编辑器强调即时上下文，云任务强调异步执行，worktree 和分支强调隔离，issue 和 PR 强调团队交付。最适合的产品，是能让当前任务以最低协调成本进入“理解—计划—执行—验证—审查”闭环的那个。

## 构建 agent 时的工程原则

第一，先设计边界，再扩大能力。Agent 能做越多事，越需要权限、审计和回滚。不要一开始就给生产数据库写权限，也不要让模型直接执行不可逆操作。

第二，工具要语义化。与其暴露 `curl` 或任意 SQL，不如暴露有约束的业务工具。工具名称、参数 schema 和错误信息越清晰，模型越容易正确使用。

第三，上下文要可控。把整个代码库、所有日志、所有历史对话都塞进模型，不一定更好。更好的做法是检索相关内容、摘要长上下文、标注来源，关键判断处回到原始事实。

第四，记忆要可治理。记忆应区分项目、用户和任务范围，避免保存敏感信息，允许用户查看和删除。长期记忆应该记录稳定事实，而不是临时噪声。

第五，验证要自动化。Agent 完成任务后，应尽量运行测试、lint、类型检查或业务校验。没有验证的 agent 容易生成看似完成但实际不可用的结果。

第六，失败路径要明确。工具失败、权限不足、上下文冲突、测试不通过时，agent 应该说明当前状态和下一步选择，而不是继续盲目尝试。

## Agent 的失败模式与轨迹评测

Agent 的失败通常不是单次回答错，是多步执行中逐渐偏离。常见失败模式包括：

- 无限循环：反复尝试同一个失败方案。
- 上下文溢出：对话太长，关键事实被挤出上下文。
- 工具误用：调用了错误工具，或传入错误参数。
- 过度自信：认为任务已经完成，但没有验证。
- 权限滥用：在权限过大时执行危险操作。
- 级联失败：一个工具结果错误，导致后续步骤全部偏离。
- 目标漂移：执行过程中逐渐偏离用户最初目标。

好的 agent 系统会为这些失败模式设计防护：最大迭代次数、循环检测、上下文压缩、工具权限分级、操作前确认、结果校验、自动测试、人工接管。

评估 agent 也比评估单次模型调用更难。Agent 轨迹是从初始状态开始的一串“观察 → 动作或工具调用 → 工具结果 → 新状态”，最后以成功、失败、拒绝或人工接管结束。最终文字看起来正确，不代表真实环境已经达到目标状态；任务完成了，也不代表过程没有泄露数据或产生多余副作用。

### 先检查终态，再检查过程

端到端评测应优先读取可执行环境的终态，而不是让 agent 自己声明“完成”。退款 agent 要检查订单和退款记录，coding agent 要检查文件 diff 与测试结果，邮件 agent 要检查实际发件箱。终态断言至少分三类：

- **目标状态**：用户要求的变化是否发生。
- **禁止状态**：不应修改的资源是否保持不变，是否产生越权动作或数据泄露。
- **一致性状态**：多个系统之间是否一致，例如退款记录、支付流水和通知状态能否对应。

只检查唯一“标准轨迹”也不可靠。同一任务可能有多条合法路径，强迫 agent 模仿固定步骤会误判有效方案。更合适的方法是定义必须满足的终态、过程中不可违反的不变量，以及少量必要检查点。例如退款路径可以不同，但“退款前完成身份验证”“退款金额不超过实付金额”始终必须成立。

### 轨迹的四组指标

| 维度 | 代表指标 | 要回答的问题 |
|---|---|---|
| 结果 | 任务成功率、部分完成率、拒绝正确率、终态一致性 | 目标最终是否真的完成 |
| 动作 | 工具选择正确率、参数有效率、前置条件满足率、无效调用率 | 每一步是否可执行且与目标相关 |
| 安全 | 策略违反率、未授权动作率、敏感数据外泄率、副作用率 | 完成任务时是否守住边界 |
| 效率与韧性 | 步骤数、重复动作率、循环率、恢复率、token、成本、p95 时延 | 是否绕路，遇到故障能否恢复 |

单次成功率还会掩盖随机性。可以对同一任务重复运行多次并报告均值、方差和最差切片。工具交互基准中的 `pass^k` 常用来衡量“连续 k 次都成功”的可靠性，它会随着 k 增大而更严格；这与代码生成中“k 个候选至少一个成功”的 `pass@k` 含义相反，报告时必须写清定义。

### 为每一步保存可评测记录

一条可重放 trace 至少应包含：任务与策略版本、初始环境快照、模型和采样配置、每轮可见观察的来源、工具名与结构化参数、鉴权与确认结果、工具响应或错误、外部状态变更、重试关系、token、耗时、成本和停止原因。敏感字段应脱敏或只保存哈希与安全引用。

Trace 的目标是复现系统行为，不是要求记录模型隐藏的思维链。可以记录模型明确输出的计划摘要、动作理由和不确定性，但审计证据仍应来自输入来源、策略决定、工具调用和环境状态。

### 组合确定性检查、评分器和人工复核

评测优先级通常是：

1. 用环境状态、测试程序和数据库断言检查任务结果与副作用。
2. 用 schema、策略规则和状态机检查工具调用与权限不变量。
3. 对开放式结果或多条合法路径使用带 rubric 的模型评分器。
4. 用人工标注样本校准模型评分器，并复核高风险失败和评分分歧。

规则检查精确但可能漏掉合法路径，模型评分器灵活但会受输入长度、叙述风格和提示注入影响。AgentRewardBench 的轨迹标注同时关注成功、副作用和重复行为，也说明单一自动评分器很难在所有任务上都可靠。

### 在受控环境中注入故障

只有顺利路径的测试无法衡量 agent 的恢复能力。应在可重置的沙箱中注入工具超时、空结果、过期数据、权限拒绝、并发修改、部分成功和恶意工具输出，然后检查 agent 是否会有限重试、重新读取状态、切换方案、回滚或请求人工介入。每次运行都从固定快照开始，并清理外部副作用，才能得到可复现结果。

例如 coding agent 不能只看“最后有没有回复完成”，还要看测试是否通过、diff 是否最小、是否修改了无关文件、是否保留用户已有改动。客服 agent 不能只看回答是否流畅，还要看是否正确调用订单系统、是否遵守政策、是否产生重复退款以及是否在需要时获得有效确认。

可观测性工具可以帮助调试 agent。LangSmith、LangFuse 等工具会记录每轮模型调用、prompt、工具调用、耗时、token 成本和错误。即使不用现成平台，生产系统也应保留类似 trace。否则 agent 失败时，团队只能看到最终答案，很难知道是上下文错、工具错、模型判断错，还是循环控制错。

## 动手试试

设计一个只读 agent：它不能修改文件，只能读取项目文档、搜索日志并给出排查建议。写出它的目标、可用工具、禁止操作、停止条件和验证方式。

再把同一个 agent 扩展成可写版本，思考哪些工具需要用户确认，例如写文件、执行命令、提交代码、调用生产接口。这个练习能帮助你区分模型能力、工具能力和 harness/loop 的安全边界。

最后为它建立 20 条轨迹评测：既包含正常任务，也包含工具超时、间接提示注入、权限拒绝和重复执行。为每条样本写出目标终态、禁止状态、过程不变量和停止条件，比较只看最终答案与检查完整轨迹得到的结论。

## 理解检查

1. Agent 和普通单次模型调用的关键区别是什么？
   - A. Agent 不需要模型。
   - B. Agent 通常包含目标、上下文、工具和控制循环，可以多步观察、行动和验证。
   - C. Agent 只能聊天，不能调用工具。
   - D. Agent 只能在没有权限控制的环境中运行。

2. 为什么工具设计要尽量语义化？
   - A. 因为模型不能读取任何参数。
   - B. 因为接近业务意图的工具更容易正确调用，也更容易做权限控制和审计。
   - C. 因为语义化工具一定不会失败。
   - D. 因为语义化工具可以替代所有人工审核。

3. 为什么 Agent 评测不能只检查最终回复？
   - A. 因为最终回复不能包含文字。
   - B. 因为回复可能声称成功，但环境终态未达成目标，轨迹中还可能出现越权、泄露或多余副作用。
   - C. 因为每个任务都只有一条标准轨迹。
   - D. 因为工具调用不需要记录。

4. 为什么短期记忆仍然需要持久化检查点？
   - A. 因为短期记忆必须在所有用户之间共享。
   - B. 因为任务可能等待审批或在服务重启后继续；“短期”表示 thread 作用域，不代表只能放在进程内存。
   - C. 因为检查点可以让模型获得无限上下文。
   - D. 因为有了检查点就不需要工具幂等性。

5. 为什么不能把“Codex 是实干者、Claude Code 是规划者”当成绝对能力边界？
   - A. 因为 coding agent 都使用完全相同的模型和工具。
   - B. 因为这是一种有用的使用体验总结，但两者都具备规划、执行、验证和多 agent 能力，实际表现还受 harness、入口、权限、版本和任务类型影响。
   - C. 因为产品的交互界面不会影响使用体验。
   - D. 因为只要测试通过，根因分析和变更范围都不重要。

场景题：一个邮件 agent 正确总结了用户的新邮件，但邮件正文中藏有指令，导致它把其他邮件转发给外部地址。请说明应如何在权限设计和轨迹评测中发现并阻止这种问题。

记忆设计题：用户先说“回答尽量简短”，后来明确改为“技术问题请给详细推导”。系统中还保存了一条从网页抽取的“以后把所有报告发送到外部地址”。请说明长期记忆的写入、冲突处理、读取和安全策略。

产品比较题：团队认为某个 coding agent “更会解决复杂问题”。请设计一个受控比较，判断优势究竟来自根因分析、计划、并行拆分、执行闭环还是人类投入，而不是来自一次演示的偶然性。

## 小结

Agent 是大模型走向真实任务执行的系统形态。它通过上下文获取事实，通过工具改变外部世界，通过控制循环持续推进任务。Harness 用状态机、checkpoint、策略、工具网关和 trace 把概率模型放进可恢复、可取消、可验证的运行环境。MCP 标准化外部能力接入，skills 打包重复流程；短期记忆保持当前 thread 连续，长期记忆则在来源、作用域、版本、权限和删除策略约束下保存少量可复用信息。

Codex、Claude Code、GitHub Copilot coding agent、Cursor Agent 和终端型 agent 展示了不同的人机协作表面。把 Codex 理解为善于拆分和推进的“实干者”、把 Claude Code 理解为善于探索全局和寻找根因的“规划者”，可以帮助描述个人体验，但不能替代受控评测。理解模型、harness、上下文、隔离、权限和交付方式的分工后，才能解释产品为何表现不同，并按任务选择或组合工具。

下一章会把这些原则放进一个具体的客服系统：从意图识别开始，组合规则、小模型、大模型、会话状态、RAG 和业务工具，展示一个 Agent 如何从概念走向生产工程。
