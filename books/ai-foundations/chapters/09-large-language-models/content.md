# 大语言模型如何工作

> **更新时间**：2026-07-29
>
> **事实审校**：训练、对齐与 RAG 描述已按原始论文复核；模型规模、数据配方和产品能力以公开材料及本次更新时间为边界。

大语言模型通常基于 Transformer，并在海量文本上进行自监督预训练。它的基本目标很简单：给定上下文，预测下一个 token。但当模型、数据和计算规模足够大时，这个简单目标会带来非常丰富的能力。

## 语言模型的目标

输入“今天下午三点开”时，后面可能是“会”“始”“门”等不同 token。系统不能查出唯一固定答案，而要根据上下文给每种续写分配可能性。语言模型就是从这种开放式预测问题出发。

语言模型不会给出一个确定答案，它输出的是下一个 token 的概率分布。生成时，系统根据这个分布选择 token，再把新 token 加入上下文，继续预测下一个。

如果总是选择概率最高的 token，输出更稳定但可能保守。提高 temperature 会让采样更随机，输出更多样，但也更容易偏离事实。top-p 等采样策略会限制候选 token 集合，在多样性和稳定性之间取舍。

可以用一句话走一遍生成过程：

```text
输入：今天天气真好，我们去
模型预测下一个 token：
  公园 35%
  爬山 20%
  散步 15%
  学校 5%
  其他 25%
```

如果系统选择了“公园”，新的上下文就变成：

```text
今天天气真好，我们去公园
```

模型再预测下一个 token：

```text
散步 25%
玩 20%
晒太阳 10%
跑步 8%
其他 37%
```

如果继续选择“散步”，上下文又变成：

```text
今天天气真好，我们去公园散步
```

整个生成过程就是不断重复：

```text
看已有上下文 -> 预测下一个 token 概率分布 -> 选择一个 token -> 追加到上下文 -> 再预测
```

模型回答问题，并不是从数据库中查出一句固定答案，而是在上下文约束下生成一串高概率 token。

例如问“巴黎是哪个国家的首都”，模型很可能生成“法国”，因为训练中这种模式极其常见。但如果问“我们公司 2026 年 Q2 内部差旅政策的报销上限是多少”，模型如果没有检索内部文档，只能根据相似文本猜测。两类问题看起来都是问答，可靠性来源完全不同。

## 采样参数如何影响输出

代码补全希望稳定地选择最可能结果，头脑风暴却希望看到多个合理方向；同一个概率分布不能同时满足两种体验。生成系统因此需要决定候选范围有多大、低概率选项有多少机会被选中。

temperature 可以理解为控制模型“有多大胆”。temperature 越低，模型越倾向于选择最高概率 token，输出更稳定、更可重复，但也更保守。temperature 越高，低概率 token 被选中的机会增加，输出更有变化，但也更容易跑偏。

当 temperature 接近 0 时，模型几乎总是选择概率最高的 token。这适合代码生成、结构化抽取、分类、格式转换等需要稳定性的任务。写诗、头脑风暴、广告文案等任务可以适当提高 temperature，让模型产生更多不同候选。

top-p，也叫 nucleus sampling，控制候选集合大小。假设 top-p = 0.9，模型会先把候选 token 按概率从高到低排序，只保留累计概率达到 90% 的那一小批候选，剩下长尾 token 直接排除。这样即使 temperature 较高，也不至于从极低概率的离谱 token 中采样。

top-k 是另一种常见采样参数。它只允许模型从概率最高的 k 个 token 中选择。例如 top-k = 40 时，排名第 41 之后的候选会被排除，即使它们的累计概率还没有达到某个阈值。top-k 更像固定抽签箱大小，top-p 更像按概率质量动态决定抽签箱大小。

可以把 temperature、top-k 和 top-p 的关系理解为：temperature 调整候选之间的随机性，top-k 限制最多有多少候选能参与，top-p 限制候选集合的累计概率范围。实际应用中，如果你要稳定回答，使用较低 temperature 和较严格格式约束；如果你要创意发散，可以提高 temperature，但仍用 top-p 或 top-k 控制离谱输出。

可以用任意支持采样参数的文本生成接口做对照实验；不同模型支持的参数和值域可能不同，应以对应版本文档为准：

```python
prompt = "用一句话解释什么是梯度下降"

stable = model.generate(prompt, temperature=0.0)
creative = model.generate(prompt, temperature=1.2)

print(stable)
# 可能更确定：梯度下降通过沿损失函数下降方向更新参数来减小误差。
print(creative)
# 可能更多样：梯度下降像沿着山坡寻找更低处，逐步走向误差较小的位置。
```

## 预训练

要让模型掌握语言和大量模式，人工为互联网规模文本逐条写标签不现实。文本自身却天然提供了“前文之后实际出现什么”这个训练信号，因此可以在不额外标注每条样本的情况下学习。

预训练使用海量文本，让模型学习语言结构、世界知识、代码模式和推理样式。训练目标通常是预测下一个 token。这是一种自监督学习，因为文本本身就提供了输入和目标。

规模是大语言模型能力提升的重要因素。更多数据、更大模型和更多计算，通常会带来更强的泛化能力。但规模不是唯一因素。数据质量、架构细节、训练稳定性和后续对齐都会影响模型最终表现。

预训练数据通常包括网页文本、书籍、论文、代码、百科、论坛讨论、问答数据和其他公开或授权语料。不同模型的数据配比不同，最终能力也会不同。代码数据多的模型通常更擅长编程；高质量书籍和论文比例高的模型，可能在长文本结构、知识密度和推理表达上更稳。

“大”可以从三个角度理解。第一是参数量，也就是模型内部可训练数字的数量；第二是数据量，通常以 token 数计；第三是计算量，也就是训练时消耗了多少 GPU 时间。更多参数让模型有更大容量，更多数据提供更多模式，更多计算让模型有机会把这些模式学进去。

参数不是知识条目的列表。它更像一套巨大函数的内部旋钮。训练不断调整这些旋钮，让模型在海量上下文中更擅长预测下一个 token。模型可能因此记住一些事实，也可能学到语法、风格、代码结构、推理模板和常见任务模式。

规模可以用数量级建立直觉，但不要把这些数字理解成固定分界线。不同团队的训练数据质量、模型结构和训练策略不同，同样参数量的模型能力可能差很多。

| 模型类别 | 参数量量级 | 训练数据量级 | 训练成本直觉 |
|---|---:|---:|---|
| 小型语言模型 | 1B-7B | 数千亿到 1T+ token | 单机多卡或小集群可训练/微调 |
| 中型语言模型 | 7B-70B | 1T-15T token | 多机多卡集群，训练和调参成本明显上升 |
| 大型语言模型 | 70B+ | 10T+ token | 大规模集群，需要专门的数据、并行和稳定性工程 |

这个表只给规模感。实际选型时，开发者更应关注任务需求、推理成本、上下文长度、延迟和可部署性，而不是只看参数量。

当模型规模、数据规模和计算规模同时增长时，有些能力会在小模型上不明显，却在大模型上突然变得可用，研究者常称为涌现能力。例如更复杂的指令遵循、代码生成、多步推理和少样本学习。涌现不是魔法，而是简单训练目标在足够规模下产生的复杂行为；但它的边界仍然需要通过评估来确认。

### 预训练数据工程

"数据决定模型上限"不仅是一句口号，预训练数据的质量直接决定模型能力。

**去重**：训练数据中重复内容会导致模型在重复文本上过拟合，浪费训练算力。一种常见方法是基于 MinHash 估计文本集合的相似度，再按阈值识别近似重复；实际数据管线还会组合 URL、文档、段落和精确哈希等多级规则。

**质量过滤**：原始 Common Crawl 数据中只有少量是高质量内容。常见做法是用一个轻量分类器（比如 fastText）给每页打质量分，过滤掉广告、垃圾、模板页面。更精细的方法是：用高质量语料（维基百科、书籍）训练分类器，然后从 Common Crawl 中筛选出"像维基百科风格"的页面。

**数据混合比例**：这是预训练中最有"炼丹"感的决策。以初代 LLaMA 论文公开的训练配方为例：CommonCrawl 约 67%、C4 约 15%、GitHub 约 4.5%、Wikipedia 约 4.5%、Books 约 4.5%、arXiv 约 2.5%、Stack Exchange 约 2%。这只是一个已公开的历史配方，不代表后续 Llama 系列或其他模型采用相同比例。关键经验：
- 增加代码比例 → 模型推理和结构化输出能力更强
- 增加学术比例 → 知识准确性和专业性更强
- 增加对话数据 → 指令跟随更自然

**合成数据**：Self-Instruct 和 Evol-Instruct 方法可以用强模型生成训练数据。但合成数据有大坑：模型用自己生成的数据训练可能导致"模型坍缩"（model collapse），分布越来越窄。因此合成数据通常只占训练数据的 5-15%，且必须混入真实数据。

## 上下文窗口

长对话里，用户常以为模型“记得前面说过的一切”；但一次模型调用只会使用本次真正发送进去的内容。聊天历史、文档和工具结果不断增长后，系统必须决定哪些信息仍能被模型看见。

模型每次生成都只能看到上下文窗口内的内容。prompt、历史对话、检索文档、工具结果都会占用上下文。超过窗口的内容无法直接参与当前推理。

长上下文可以容纳更多信息，但成本更高，注意力计算和 KV Cache 都会增长。同时，模型能“看到”长文本，不代表它能完美使用所有信息。长上下文中的关键信息仍可能被忽略。

因此，应用层需要管理上下文：压缩历史、选择相关文档、控制格式、避免把无关信息塞进 prompt。

一个客服对话例子：用户前 20 轮都在闲聊，最后问“那我这个订单什么时候到”。如果把全部历史都塞进上下文，会浪费 token；更好的做法是保留订单号、物流状态、最近问题等关键信息，把闲聊压缩或丢弃。

长上下文还有一个常见现象：模型能看到材料，不代表它一定会用好材料。研究和实践中经常观察到，关键信息如果埋在很长上下文的中间位置，模型更容易忽略；这常被称为 Lost in the Middle。模型可能更关注开头的任务说明和结尾的最新对话，而对中间大量材料分配的注意力不足。

因此，上下文管理不是简单“塞得越多越好”。应用层通常会做几类处理：

- 摘要历史：把多轮闲聊压缩成当前任务相关状态。
- 选择片段：只放入和当前问题最相关的文档块，而不是整篇文档。
- 结构化上下文：用标题、来源、时间、优先级标注材料，帮助模型分辨重要性。
- 去重和裁剪：删除重复、过期、低相关内容。
- 关键信息前置或后置：把必须遵守的约束放在更醒目的位置。
- 外部状态保存：不要把所有状态都压进 prompt，而是放在数据库、记忆或工具结果中按需读取。

好的上下文管理像整理会议材料。不是把所有文件堆到桌上，而是把本次决策真正需要的证据、背景和约束按顺序摆出来。

## 能力来源

大语言模型的能力来自多个层面。预训练让它掌握语言和大量模式；Transformer 让它能在上下文中建立关系；指令微调让它学会遵循人类请求；偏好对齐让它更倾向于有帮助的回答。

模型可以完成总结、改写、翻译、代码生成、问答、分类、推理辅助和工具调用等任务。但这些能力并不等于可靠知识或严格逻辑证明。模型在熟悉分布内表现更好，在陌生、对抗或需要精确事实的场景中更容易出错。

## 幻觉与不确定性

幻觉指模型生成看似合理但不真实的内容。它产生的根本原因在于生成目标是预测 token，而不是验证事实。当上下文不足、问题含糊或模型内部知识不可靠时，模型仍可能继续生成流畅文本。

缓解幻觉不能只靠“请不要幻觉”这类提示。更可靠的方法包括 RAG、工具调用、引用来源、结构化约束、结果校验和人工审核。对于高风险场景，模型输出应被视为建议，而不是最终事实。

例如法律问答系统不能只让模型直接回答“这份合同有没有风险”。更稳妥的流程是：先抽取合同条款，检索相关法规和公司法务规则，再让模型列出风险点和引用来源，最后由人工确认。模型负责提高效率，不负责最终法律判断。

幻觉可以分成几类。事实性幻觉是编造不存在的事实，例如虚构论文、政策或人物经历。推理性幻觉是中间逻辑出错，例如数学计算、条件判断或因果分析不成立。一致性幻觉是前后说法冲突，例如前面说某配置已开启，后面又说没有开启。

不同幻觉需要不同缓解方式。事实性幻觉适合用 RAG、数据库查询和引用来源缓解；推理性幻觉适合引入计算器、代码执行、规则校验或分步验证；一致性幻觉可以通过结构化输出、状态记录和自检流程降低。

还要注意，模型的自信语气不等于答案可靠。大语言模型擅长生成流畅文本，即使没有证据也可能说得很像真的。因此产品设计里最好把“事实来源”和“模型表达”分开：事实来自检索、数据库或工具，模型负责组织语言、解释和交互。

## RAG：先看它解决什么实际问题

假设你要为公司做一个制度问答助手。员工问：“出差打车能不能报销，最晚什么时候提交？”公司有几万页制度文档，不同地区、岗位和版本的规则还可能不同。这个需求表面上是“让大模型回答问题”，实际却包含几个单靠模型参数和一次 prompt 很难稳定解决的问题：

- **模型不知道私有知识**：内部制度、客服手册和项目文档通常不在公开训练数据里。
- **模型知识可能过期**：即使见过旧版本，也不知道昨天刚生效的新规则。
- **资料远大于一次上下文**：不能把几万页文档全部塞进每次请求；即使上下文放得下，成本、延迟和无关噪声也会增加。
- **回答需要依据**：员工和审核人员不仅要答案，还要知道来自哪份制度、哪个版本、哪一页。
- **知识必须可治理**：制度修改、撤回或权限变化后，系统应能更新、删除和限制访问，而不是等待重新训练模型。

所以，真正的问题不是“怎样让模型背下所有文档”，而是：**怎样在每次请求到来时，从当前用户有权访问的资料中找出少量相关证据，再让模型只基于这些证据组织答案。**

### 几种直觉方案为什么不够

第一种做法是直接询问通用模型。演示时它可能答得流畅，但遇到私有制度、最新版本或长尾条款时，只能依赖参数中不完整的旧知识，甚至会补出一个听起来合理的答案。

第二种做法是把所有文档拼进 prompt。资料很少时可以这样建立原型，但文档增长后会碰到上下文上限、token 成本、延迟、重复内容和“关键信息被大量噪声淹没”等问题。长上下文减少了检索需求，却没有自动解决资料选择、权限、更新和引用。

第三种做法是每次更新制度就微调模型。微调更适合改变回答风格、格式或稳定行为，不适合作为频繁更新事实的主要存储方式。重新训练和发布有周期，删除某条知识困难，也很难证明某句话来自哪一版原文。

第四种做法是只提供关键词搜索。搜索本身很有价值，但它通常返回文档列表，仍要用户打开、筛选和归纳；同义表达还可能让精确关键词漏掉相关资料。更理想的体验是保留搜索的可追溯性，同时让模型完成阅读、比较和解释。

### RAG 的核心思路：先找证据，再组织答案

RAG（Retrieval-Augmented Generation，检索增强生成）把这两个步骤串成一条链路：检索系统负责从可更新、可追溯的外部知识中找证据，生成模型负责结合问题与证据组织答案。原始 RAG 工作把生成模型中的参数知识称为参数化记忆，把外部稠密向量索引称为非参数化记忆；今天工程中的 RAG 已经扩展到关键词、向量、数据库、知识图谱和外部搜索等多种检索方式。

在刚才的报销问题中，一次请求可以这样处理：

1. 根据员工身份确定地区、岗位和文档权限。
2. 用“出差打车”“交通费凭证”“提交期限”等语义和关键词召回候选条款。
3. 选择最新、权威且能直接支持结论的片段，连同标题、页码和版本交给模型。
4. 模型基于这些片段回答并附引用；如果资料冲突或没有答案，就明确说明并转向人工或权威系统。

这种拆分有三个直接价值。第一，知识可以在不重新训练模型的情况下更新或删除。第二，系统可以返回文档、页码和版本，让用户检查依据。第三，团队可以分别评估“证据有没有找到”和“模型有没有正确使用证据”。但 RAG 只能提供证据，不能自动保证答案真实；过期语料、错误权限、糟糕切块和不忠实生成仍会导致失败。

### 什么时候优先考虑 RAG

RAG 特别适合“答案散落在大量外部资料中，并且需要自然语言解释”的任务，例如企业制度问答、技术文档助手、客服知识库、研究资料归纳和带来源的内容生成。资料越私有、变化越快、规模越大、引用要求越高，RAG 的价值通常越明显。

但不要把所有问题都做成文档向量检索。查询实时订单、余额和库存时，应优先调用 SQL 或权威业务 API；提交退款、发送邮件属于工具执行；固定语气和输出格式主要靠 prompt、结构化输出或微调；精确计算应交给计算器或代码。结构化查询和 API 的结果也可以作为生成证据进入广义 RAG 链路，但如果任务只是精确查一个字段，就没有必要先把数据库记录转成文档再做向量搜索。

还要先问一句：是否存在可信资料。如果知识源本身错误、缺失或互相冲突，RAG 不能凭空制造真相。系统需要暴露冲突、说明证据不足或转向权威数据源，而不是把“检索到了文字”误当成“找到了事实”。

### 两条链路：离线准备知识，在线回答问题

一套基础 RAG 可以画成两条链路：

```text
离线知识链路
数据源 → 解析/OCR → 清洗与去重 → 结构化切块 → 元数据与权限
      → 稀疏/稠密表示 → 建立索引 → 质量检查 → 发布索引版本

在线回答链路
用户与身份 → 理解/改写查询 → 权限和时间过滤 → 多路召回
           → 融合与重排 → 上下文组装 → 生成/拒答 → 引用校验
```

离线链路决定“系统有什么知识”。网页、PDF、数据库记录和工单首先要被可靠解析；标题层级、列表、表格、页码和附件关系不能在抽取时丢失。然后系统生成稳定的文档 ID 和块 ID，保存来源、版本、有效时间、租户和访问控制列表，再建立全文与向量索引。索引发布应有版本，便于回滚并保证离线评测与线上结果能够对应。

在线链路决定“这次问题看见哪些证据”。系统先从可信会话状态取得用户、租户和权限，识别查询中的实体、时间、产品版本与任务类型，再选择适合的检索器。候选经过融合、去重和重排后，才在 token 预算内组成模型上下文。最后生成器回答、引用或明确拒答，并把查询、索引版本、候选、最终证据和输出写入 trace。

### 切块不是简单按固定字数截断

检索的基本单位通常是 chunk。块太大，一个向量会混合多个主题，召回后还浪费上下文；块太小，限定条件、表头或上下段关系会被拆散。常见策略包括：

- 固定长度加重叠：实现简单，适合建立基线，但可能切断章节和表格。
- 按文档结构切分：保留标题、段落、列表、代码块和表格，更适合制度与技术文档。
- 父子块：用短子块做精确检索，把带标题和邻近段落的父块交给模型。
- 层级检索：先找文档或章节，再在局部范围找段落，适合长文档和多层目录。
- 特殊类型解析：表格按表头与行列组织，代码保留符号和文件路径，图片保留页码、区域和 OCR 文本。

重叠不是越大越好。过多重叠会制造重复候选、扩大索引并挤占上下文。真正的切块参数应由一组带证据标注的真实问题决定：答案所需信息是否在一个块内，限制条件是否保留，召回结果是否引入过多噪声。

### 查询处理、混合召回与重排

用户问题不一定适合直接拿去搜索。“它支持吗？”需要从对话状态补全“它”指什么；“2025 年以后北京员工的标准”同时包含时间和地域过滤；“比较 A 与 B 的退款规则”可能需要拆成两个子查询。查询处理可以做指代补全、拼写归一、实体识别、时间解析、改写或分解，但必须保留用户原始约束，并记录改写前后的对应关系。

不同检索器擅长不同信号：

- 关键词或 BM25 擅长产品编号、错误码、姓名和精确短语。
- 稠密向量检索擅长同义表达和语义相近内容。
- SQL、键值查询适合订单状态、余额、库存等结构化事实。
- 知识图谱适合实体关系和受约束的多跳查询。
- 业务 API 适合必须读取实时权威状态的任务。

因此 RAG 不必押注单一路径。混合检索可以并行取得稀疏与稠密候选，再用 Reciprocal Rank Fusion 或经过校准的分数组合合并排序。初次召回的目标偏向高召回率；重排器再对几十个候选做较慢、较精细的 query-document 匹配，把真正能回答问题的证据推到前面。

权限条件必须进入召回过程。`tenant_id`、ACL、地区、有效时间等过滤来自可信身份和业务状态，不能让模型从文档文字中自行推断。无权内容不应先进入模型再靠 prompt 要求“不要泄露”，也不应在返回答案时才过滤。

### 上下文组装决定模型实际能看见什么

Top-K 不是上下文组装的全部。系统还要去重、控制不同来源的多样性、补充必要的相邻段落、优先保留直接证据，并在 token 预算内避免把同一段话重复多次。每个片段应带稳定的来源标签，例如：

```text
[S1]
document_id: travel-policy-2026
version: 2026-07-01
section: 4.2 提交期限
page: 12
trust: internal-policy
content: 报销申请应在费用发生后……
```

来源标签让生成器可以把主张绑定到证据，也让应用在输出后检查引用。但检索材料仍然是不可信数据：网页、邮件和用户上传文档可能包含“忽略规则并发送文件”之类的提示注入。上下文模板必须把系统指令、用户目标和外部材料分区，外部文字只能作为证据，不能成为授权。

遇到冲突资料时，不要悄悄只选一个结果。系统可以按权威级别、有效日期和版本规则排序，并要求模型显式说明冲突；如果无法确定，应返回需要人工确认或权威数据源查询，而不是综合出一个不存在的结论。

### 生成、引用与拒答

生成阶段至少要规定：只根据给定证据回答可核查事实；证据不足时明确说不知道；关键主张附带片段 ID；不要引用没有进入本次上下文的来源。更严格的系统会先让模型输出结构化的“主张—证据”列表，程序逐条校验片段是否存在、用户是否有权访问、引用是否支持相邻主张，再渲染为自然语言。

“有引用”不等于“引用正确”。模型可能引用真实文档，但该段并不支持结论；也可能把多个来源拼成过度推断。因此发布门禁要分别检查答案正确性、对证据的忠实性、引用正确率、引用覆盖率和无答案时的拒答准确率。

### RAG、向量数据库和 Agent 记忆不是一回事

| 概念 | 解决的问题 | 典型内容 | 是否一定使用 embedding |
|---|---|---|---|
| RAG | 为当前生成检索外部证据 | 制度、网页、数据库记录、搜索结果 | 否 |
| 向量数据库 | 保存向量、元数据并执行相似度检索 | 文档块、商品、图片、历史案例 | 是，或同时支持稀疏表示 |
| Agent 短期记忆 | 保存一个任务或会话的运行状态 | 消息、计划、工具结果、待审批动作 | 否 |
| Agent 长期记忆 | 跨会话保存可复用事实或经验 | 用户偏好、项目事实、成功案例 | 可选；只是检索方式之一 |

向量数据库可以支持 RAG，也可以支持推荐和去重；RAG 可以完全不使用向量数据库；长期记忆可以借用 RAG 的检索技术，但还需要写入策略、作用域、冲突处理、过期和删除机制。第 16 章会详细讨论这套记忆生命周期。

### 用端到端伪代码串起流程

```python
def answer(user, question):
    identity = authenticate(user)
    query = analyze_query(question, conversation_state=user.thread_state)

    filters = build_trusted_filters(
        tenant_id=identity.tenant_id,
        acl=identity.roles,
        valid_at=query.requested_time,
    )

    dense = vector_search(query.semantic_query, filters=filters, top_k=40)
    sparse = keyword_search(query.lexical_query, filters=filters, top_k=40)
    candidates = reciprocal_rank_fusion(dense, sparse)
    evidence = rerank_and_pack(question, candidates, token_budget=6000)

    if not evidence_is_sufficient(question, evidence):
        return refusal_with_search_diagnostics()

    draft = generate_grounded_answer(question, evidence)
    return verify_claims_and_render_citations(draft, evidence)
```

这段代码省略了大量实现细节，却揭示了重要边界：身份与过滤条件由应用提供，检索返回的是候选证据，模型不能自己授予访问权限，最终答案还要接受引用和业务规则校验。

## RAG 评测：拆开检索、生成和证据

RAG 把外部资料放进上下文，不代表答案自然可靠。一条 RAG 链路至少包含语料、切分与索引、查询改写、召回、重排、上下文组装、生成和引用。只看最终回答，无法判断问题究竟出在哪一层。

### 先构造可诊断的评测集

一条高质量 RAG 样本不应只有“问题 + 标准答案”，还应尽量记录：

- 可接受答案或评分规则，而不是只允许一种措辞。
- 支撑答案的文档 ID、版本、段落或原文片段。
- 相关文档集合，便于计算检索指标。
- 是否应该拒答，以及资料不足时允许输出什么。
- 租户、权限、时间和语言等过滤条件。
- 样本所属切片，例如常见问题、长尾问题、多跳问题、时效问题和对抗问题。

评测语料与生产索引要保留版本。否则文档更新后，昨天的标准答案可能已经过期，团队会把“知识变化”误判成“模型退化”。对于动态事实，还要记录答案有效时间，并在测试时固定检索快照或明确允许访问的时间范围。

### 分层指标比一个总分更有用

| 层级 | 主要问题 | 常用指标或检查 |
|---|---|---|
| 语料与索引 | 正确资料是否存在、是否新鲜、是否正确分块 | 文档覆盖率、索引新鲜度、重复率、权限标签完整率 |
| 召回与重排 | 相关证据有没有进入前 k 个结果，排序是否合理 | Recall@k、Precision@k、MRR、nDCG、上下文精确率与召回率 |
| 上下文组装 | 是否把关键片段保留下来，同时控制噪声 | 有效证据占比、截断率、重复片段率、token 数 |
| 生成 | 回答是否正确、完整，并忠实使用证据 | 答案正确性、完整性、faithfulness、拒答准确率 |
| 引用 | 引用是否真的支持相邻主张，关键主张是否都有证据 | 引用正确率、引用覆盖率、来源可访问率 |
| 端到端 | 用户任务是否解决，代价是否可接受 | 任务成功率、人工接管率、p50/p95 延迟、每请求成本 |

`Recall@k` 关注所有相关资料中有多少被召回；`Precision@k` 关注前 k 个结果中有多少真正相关。MRR 看第一个相关结果出现得多早，nDCG 适合存在多级相关性并且顺序重要的场景。检索指标需要人工相关性标签或可信的弱标签，不能让待评模型同时生成标签并给自己打分。

生成评测要把几个概念分开：

- **答案正确性**：回答是否满足标准答案或业务规则。
- **完整性**：问题要求的关键点是否都覆盖。
- **忠实性 / groundedness**：回答中的可核查主张是否能由本次检索证据支持。
- **引用正确率**：给出的引用是否真的支持对应主张。
- **引用覆盖率**：需要证据的关键主张中，有多少附带了有效证据。
- **拒答准确率**：资料不足、冲突或无权限时，系统能否停止猜测。

一个答案可能碰巧正确，却没有被检索证据支持；也可能完全忠实于一篇过期文档，却给出错误结论。因此正确性和忠实性必须分别报告。

### 用四种结果快速定位故障

| 检索到关键证据 | 最终答案正确 | 更可能的问题 |
|---|---|---|
| 是 | 是 | 正常样本，仍需检查引用和成本 |
| 是 | 否 | 生成器忽略、误读或截断了证据 |
| 否 | 是 | 可能依赖模型记忆、答案泄漏或偶然猜中 |
| 否 | 否 | 优先排查语料、查询、召回和重排 |

这张表能避免一个常见误区：最终准确率下降时立刻更换大模型。如果关键文档从未进入上下文，换更强生成器通常治标不治本；如果 Recall@k 很高但答案仍错，才应重点检查上下文排序、提示、生成和引用绑定。

### 评测自动化仍需要校准

确定性规则应优先用于文档 ID、权限、日期、数值、JSON schema 和引用链接检查。LLM-as-judge 适合评价语义正确性、完整性和忠实性，但要用人工标注子集校准，并监控不同语言、答案长度、模型家族和提示格式上的偏差。不要只报告评分模型给出的平均分，还应保存错误样本并检查评分器的假阳性和假阴性。

发布前至少要覆盖无答案、证据冲突、长尾实体、过期文档、跨文档推理、权限隔离和恶意文档等切片。线上则持续记录查询、召回文档及版本、重排分数、最终引用、用户反馈、延迟与成本。只有保留这条证据链，离线回归和线上事故才能重现。

## Prompt 的本质

同一个模型既能总结又能翻译，还能按 JSON 输出；模型权重不会自动知道当前用户究竟要哪一种行为。应用必须在本次输入中明确任务、材料、约束和期望格式。

既然大语言模型是在上下文中预测下一个 token，prompt 的作用就是设置上下文条件。更清晰、更具体、更结构化的 prompt，会让模型更容易生成符合目标的内容。

prompt 工程不是用自然语言“编程”模型，而是给模型提供更好的任务边界。比如告诉模型角色、输入格式、输出格式、禁止事项、示例和评估标准，本质上都是在改变条件概率分布，让目标输出变得更可能。

现代模型接口通常会把消息分成不同角色。system prompt 用来设置全局行为和边界，例如“你是客服助手”“不要输出未验证事实”“必须用 JSON 返回”。user prompt 是用户当前提出的任务或问题。assistant message 则是模型之前的回复。把这些角色分开，可以让应用把长期规则和单次请求分层管理。

System prompt 适合放稳定约束：角色、语气、输出格式、安全边界、工具使用规则。User prompt 适合放本次任务、输入材料和用户意图。不要把所有东西都塞进 system prompt，因为过长的全局指令会增加成本，也可能和用户任务冲突。可靠系统通常会把 system prompt、用户输入、检索材料、工具结果和输出 schema 分开组织。

一个模糊 prompt 是：

```text
帮我分析这份合同。
```

更好的 prompt 会明确任务：

```text
请从付款条款、违约责任、保密义务和自动续约四个角度审查下面合同。
输出 JSON 数组，每个风险点包含：
- clause: 相关条款原文
- risk: 风险说明
- severity: high / medium / low
- suggestion: 修改建议
如果没有证据，不要编造条款。
```

两者调用的是同一个模型，但后者给出了更明确的生成轨道。对于稳定业务系统，仅靠 prompt 仍然不够，还需要检索、工具、校验和监控；但好的 prompt 是可靠系统的第一层约束。

## 结构化输出与工具调用

在工程系统中，模型输出往往不是给人直接阅读，而是要被程序继续处理。此时最怕模型返回一段看似合理但无法解析的文本。例如你希望得到 JSON，模型却多写了几句解释；你希望字段叫 `risk_level`，模型却写成 `severity`。结构化输出就是为了解决这个问题：让模型按指定 schema 返回可解析结果。

结构化输出可以通过 prompt 约束，也可以通过模型接口的 JSON schema、response format 或类似机制实现。后者通常更可靠，因为系统会把格式要求作为解码约束或强校验的一部分。即便如此，业务侧仍应做解析、字段校验和异常处理，不能假设模型永远返回完美 JSON。

Function calling 可以理解为更进一步的结构化输出。模型不直接执行动作，而是选择要调用的函数，并生成参数。例如用户问“查一下订单 1234 的物流状态”，模型可以输出：

```json
{
  "tool": "get_shipping_status",
  "arguments": {
    "order_id": "1234"
  }
}
```

真正查询数据库的是应用程序，不是模型本身。模型负责理解意图和组装参数，系统负责权限检查、函数执行、错误处理和结果回传。RAG、结构化输出和 function calling 经常组合使用：先检索资料，再让模型按 schema 提取结论；或者先让模型决定调用哪个工具，再把工具结果放回上下文生成最终回答。

工具调用是 Agent 系统的基础能力之一。第 16 章会进一步讨论多轮计划、执行、验证、重试和停止条件；这里先记住一点：让模型“会说”不等于让系统“能做”，真正的动作必须由受控的外部程序执行。

## 动手试试

找一个支持调整 temperature 的模型接口，使用同一个 prompt 分别设置较低和较高 temperature，比较输出的稳定性和多样性。适合测试的 prompt 是开放式任务，例如“给一个 AI 学习网站起 10 个名字”，而不是只有唯一答案的问题。

再做一个上下文实验：把同一条关键信息分别放在 prompt 开头、中间和结尾，观察模型是否都能准确引用。这个练习能帮助你理解上下文窗口不是无限可靠的记忆。

做一次方案选型练习：分别为“查询公司制度并引用原文”“查询当前订单状态”“自动提交退款申请”“把所有回复改成固定品牌语气”选择主要方案。先在 RAG、SQL/API、受控工具调用、prompt/微调中做选择，再说明是否需要把两种方案组合起来。重点不是记住术语，而是从知识是否外部、数据是否实时、任务是否产生动作、行为是否需要长期改变来判断。

为一个最小 RAG 准备 20 个问题，其中至少包含 5 个无答案或资料冲突的问题。分别记录 Recall@k、答案正确性、忠实性、引用正确率和拒答准确率，再用“是否检索到关键证据 × 最终答案是否正确”的四种情况定位错误。

## 小结

大语言模型是基于上下文预测 token 的概率模型。它通过预训练学习大量模式，通过对齐变得更会遵循指令。temperature、top-p、上下文窗口和 prompt 都会影响生成结果。

理解这些机制后，开发者就能把模型看成一个强大的概率组件，而不是绝对正确的知识库。可靠 AI 应用通常需要把模型生成、外部知识、工具调用、结构化约束和结果校验组合起来。RAG 的价值在于让知识可更新、证据可追溯和故障可分层诊断，而不是承诺接入向量库后永不幻觉。

下一章会继续追问一个工程上很重要的问题：模型参数固定后，能否通过更长思考、多路径采样、验证器和工具，为复杂任务动态增加推理时计算，并把额外成本真正转化为更可靠的答案。
