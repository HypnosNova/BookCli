# Embedding 与表征学习

> **更新时间**：2026-07-29
>
> **事实审校**：表征学习、相似度与向量索引原理已按原始论文复核；具体模型和数据库能力以本次更新时间为边界。

Embedding 把离散对象映射到连续向量空间，让模型能用数学方式处理文字、图片、用户、商品、代码片段和文档。

## 为什么需要向量表示

计算机不能直接理解“苹果”“香蕉”“汽车”这些词的语义。最朴素的表示方法是 one-hot：为词表中每个词分配一个位置，该词对应位置为 1，其他为 0。

one-hot 简单，但有两个问题。第一，它非常稀疏，词表越大向量越长。第二，它无法表达语义关系。在 one-hot 空间中，“苹果”和“香蕉”的距离与“苹果”和“汽车”的距离没有本质区别。

假设词表有 10 万个词，one-hot 表示下每个词都是一个 10 万维向量。“苹果”的向量只有“苹果”所在位置是 1，其他位置全是 0；“香蕉”也是如此，只是 1 出现在另一个位置。两个不同词的 one-hot 向量互相垂直，计算相似度时几乎看不出任何语义关系。结果就是：“苹果”和“香蕉”的相似度，与“苹果”和“发动机”的相似度一样低。

Embedding 解决了这个问题。它把对象映射为较短的稠密向量。语义相似的对象，在向量空间中通常更接近。

例如一个电商系统可以给商品学习 embedding。跑鞋、篮球鞋、运动袜的向量可能彼此接近，而跑鞋和冰箱距离较远。这样系统就能做“相似商品推荐”，即使两个商品标题没有完全相同的关键词。

Embedding 向量通常是几十维到几千维。比如一个文本 embedding 模型可能把一段话表示成 768、1024 或 1536 个数字。维度越高，理论上越能容纳丰富语义，但存储和计算成本也越高。可以把维度想成描述一个对象的特征数量：只用“身高”一个维度描述人，信息很少；加入体重、年龄、职业、城市、兴趣等维度，描述就更丰富。

当然，embedding 的每一维通常不是人能直接命名的“身高”“职业”。它们是模型在训练中自动形成的内部坐标。单独看某个数字未必有清晰含义，但整个向量的方向和位置可以表达语义关系。

## 文本如何变成 token

用户输入的是字符串，神经网络执行的却是矩阵计算。系统必须先决定“多大一段文本算一个可复用单位”，再把每个单位映射成整数；切得太粗会遇到词表膨胀和生词，切得太细又会让序列变长。这个入口问题由 tokenization 处理。

在进入 embedding 层之前，文本还需要先被切成 token。模型不能直接读取原始字符串，它实际看到的是一串 token id。token 可以是一个字、一个词、一个子词，也可以是标点、空格或特殊符号片段。

最简单的想法是按字符切分。中文里这看起来还算自然，因为每个汉字本身承载一定语义；但英文如果按字符切分，`training` 会变成 `t r a i n i n g`，序列变长，模型还要自己学会哪些字符组合成词。另一个想法是按词切分，但这会遇到生词问题：词表里没有的新词、拼写变体、复合词、代码标识符和多语言文本都会很麻烦。

现代语言模型通常使用子词切分。它介于字符和整词之间：常见词可以作为一个 token，少见词可以拆成几个子词。这样既不会让词表无限膨胀，也能处理没见过的新词。例如英文里的 `unbelievable` 可能被拆成类似 `un`、`believ`、`able` 的片段；代码里的 `getUserProfile` 也可能被拆成几个可复用片段。

BPE，也就是 Byte Pair Encoding，是一种常见子词算法。核心思路很简单：先从很小的单位开始，例如字符或字节；统计训练语料中最常一起出现的相邻片段；把高频组合合并成新片段；反复重复这个过程，直到得到目标大小的词表。高频词会逐渐合成较完整的 token，低频词则保留为更小片段。

WordPiece 和 SentencePiece 也是常见 tokenizer 方案。WordPiece 常见于 BERT 系列，倾向于选择能提高语言模型似然的子词；SentencePiece 则把文本当作原始字符流处理，不强依赖空格分词，因此对中文、日文、混合语言和没有天然空格边界的文本更方便。对初学者来说，不必先记住算法细节，关键是理解：tokenizer 决定文本如何被切开，也决定这些片段如何映射成数字 id。

看一个简化例子：

```text
原文：AI模型会处理tokenization。

可能的 token：
[AI] [模型] [会] [处理] [token] [ization] [。]

对应 token id：
[18423, 9120, 340, 7821, 5963, 17328, 13]
```

不同 tokenizer 的切法可能不同。中文可能按字、词或子词混合切；英文长词可能被拆开；标点和空格也可能单独占 token。实际系统里，调用成本、上下文窗口和推理延迟通常都按 token 计算，而不是按字数或单词数计算。因此同样长度的文本，在不同语言、不同 tokenizer 下可能占用不同 token 数。

tokenization 还会影响模型能力边界。如果某个专业词经常被拆成很多碎片，模型处理它的成本更高；如果代码、数学符号或罕见语言被切得很碎，模型可能更难形成稳定表示。训练语言模型时，tokenizer 是模型输入层的一部分，不是无关紧要的预处理工具。

## Embedding 是怎么学出来的

One-hot 解决了“怎样编号”，却让任意两个词都同样远，无法表达猫比汽车更接近狗。真实词表巨大，也不可能靠人工把每个对象摆到合适位置，因此向量之间的关系需要从任务反馈中学习。

Embedding 是在训练目标中学出来的，开发者并不手工编写。模型会根据任务不断调整向量的位置，让有用的对象靠近，让不相关或容易混淆的对象分开。

在语言模型中，经常出现在相似上下文里的词，向量会逐渐接近。例如“跑鞋”“运动鞋”“篮球鞋”经常和“运动”“尺码”“鞋底”“透气”等词一起出现；“冰箱”则常和“冷藏”“家电”“容量”“压缩机”一起出现。模型在大量文本中反复观察这些共现关系后，会把它们组织到不同语义区域。

可以用新员工观察公司关系来类比。刚入职时，你不知道谁和谁关系近。但观察一个月后，你会发现甲和乙总是一起开会、一起吃饭、一起讨论项目；丙则经常和另一个团队协作。慢慢地，你脑中会形成一张“人际关系图”。Embedding 就像模型通过观察大量数据后画出的关系图，只不过这张图不是二维纸面，而是高维向量空间。

训练目标决定了 embedding 学到什么。商品推荐模型会让经常被同一用户点击、购买或比较的商品靠近；搜索模型会让问题和相关文档靠近；图文模型会让图片和对应描述靠近。没有一种 embedding 对所有任务都最好，关键要看它的训练数据和训练目标是否匹配你的场景。

## 向量空间的直觉

把对象变成一串数字还不够，系统最终要回答“哪些对象更相似”“一个方向代表什么变化”。只有距离和方向具有任务含义，向量表示才能支持检索、聚类和推荐。

向量空间中可以计算距离和相似度。文本检索中常用余弦相似度，衡量两个向量方向是否接近。如果一个问题向量和某段文档向量相似，就说明这段文档可能与问题相关。

余弦相似度可以想象成比较两支箭的方向。两支箭方向完全相同，相似度接近 1；方向垂直，相似度接近 0；方向相反，相似度接近 -1。它重点关注“方向是否一致”，而不是箭有多长。

为什么语义搜索常用余弦相似度？因为一段长文本和一段短文本可能长度不同、向量大小不同，但只要它们讨论的是同一主题，方向可能接近。余弦相似度能减少“向量长度”带来的影响，更专注于语义方向。

这种机制让“语义搜索”成为可能。传统关键词搜索要求词面匹配，而向量检索可以找到表达不同但语义接近的内容。例如“如何降低模型延迟”和“推理加速方法”可能没有完全相同关键词，但 embedding 可能让它们靠近。

再比如企业知识库中，用户问“报销打车费需要什么材料”，文档标题可能叫“差旅交通费用凭证规范”。关键词搜索可能因为没有“打车费”而排不到前面，向量检索则可能通过语义相似找到相关文档。

向量空间也会出错。两个文本在语义上接近，不代表它们一定能回答同一个问题。例如“差旅报销标准”和“差旅报销申请流程”很接近，但前者回答金额和规则，后者回答操作步骤。如果检索系统只看向量相似度，可能召回看似相关但不能解决问题的片段。因此实际系统常把向量检索、关键词检索、重排模型和业务过滤组合使用。

## 词向量与上下文表示

早期词向量为每个词学习固定表示。但自然语言中存在多义词。例如“苹果”可能指水果，也可能指公司。固定词向量无法根据上下文改变含义。

Transformer 模型中的表示是上下文相关的。同一个 token 在不同句子中会得到不同表示。模型通过 attention 读取上下文，从而决定当前词在此处的含义。

这是现代语言模型比传统词向量更强大的地方：它表示的不再是词本身，而是词在上下文中的角色。

例如：

```text
我买了一个苹果，味道很甜。
苹果发布了新的芯片。
```

如果只使用固定词向量，“苹果”在两句话里是同一个向量。但在上下文表示中，第一句的“苹果”会更接近水果、味道、食物；第二句的“苹果”会更接近公司、芯片、发布会。模型并不只是查词典，而是在上下文中重新计算这个 token 的表示。

## 表征学习

传统机器学习依赖人先决定边缘、词频、颜色等特征；面对复杂图片、语言和音频，这些规则很难覆盖，也难跨任务复用。深度学习因此把“应该提取什么特征”本身交给训练。

表征学习指模型自动学习有用特征。传统机器学习中，开发者常常手工设计特征。深度学习中，模型可以从原始数据中逐层学习表示。

图像模型从像素学习边缘、纹理和对象；语言模型从 token 学习语法、语义和任务关系；多模态模型则把图片和文本映射到同一个向量空间，使”图文匹配”和”看图问答”成为可能。

多模态 embedding 是一个很有代表性的例子。CLIP 这类模型会同时训练图片编码器和文本编码器，让匹配的图片和文字靠近，不匹配的远离。一张橘猫照片和“一只橘猫趴在沙发上”这段文字，在共享向量空间中会很接近。这样就可以用文字搜索图片：先把查询文本变成向量，再和图片库中的图片向量比较相似度。

这类能力的关键在于：图片和文本被投影到了同一个可比较的空间。只要两种输入能变成同一空间中的向量，就可以做跨模态检索、匹配和推荐。

好的表征可以迁移。一个在大规模数据上预训练的模型，其中间表示往往能帮助许多下游任务，这也是预训练模型能复用的基础。

## 向量检索、向量数据库与 RAG

为什么生成模型还需要检索？假设公司有几万页制度、产品和技术文档：通用模型不知道内部资料和刚发布的版本；把全部文档塞进一次请求既放不下，也会增加成本和噪声；只返回搜索结果，又要用户自己逐篇阅读。真正需要的是先从大量资料中找出与当前问题有关的少量证据，再让模型基于证据解释、引用或在资料不足时拒答。

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）要解决的问题。它会在模型生成之前检索外部证据。Embedding 是常用的检索手段，但不是 RAG 的全部：生产系统还可能使用关键词检索、SQL、知识图谱、网页搜索和业务 API。第 9 章会从实际问题出发讲完整 RAG 链路；本节先回答两个更基础的问题：相似向量怎样被快速找到，以及向量数据库究竟保存了什么。

### 从最近邻搜索开始

假设文档块已经被编码成向量 $d_1,d_2,\ldots,d_n$，查询被编码成向量 $q$。检索器要按相似度找出前 $k$ 个文档。常见度量包括：

- 余弦相似度：比较方向，常用于已经归一化的文本向量。
- 点积：同时受方向和模长影响，一些 embedding 模型直接以它为训练目标。
- 欧氏距离：比较空间中的直线距离。

距离函数必须和 embedding 模型的训练及使用说明一致。不能因为两个系统都存“向量”，就假设它们的向量可以混用；维度相同也不代表处于同一个语义空间。

最直接的做法是精确最近邻搜索：查询时逐个比较所有向量。它结果确定、适合建立质量基线，在数据量不大、批量计算或硬件加速充分时也可能完全够用。随着数据规模、维度和并发增加，系统才通常转向近似最近邻（ANN, Approximate Nearest Neighbor）索引，用可控的召回损失换取更低的延迟或内存成本。是否需要 ANN 应通过本地数据和服务目标测量，不能只按一个固定数据量阈值决定。

### 向量索引不等于向量数据库

向量索引解决的是“怎样快速找近邻”。向量数据库还要解决数据的保存、更新、过滤、隔离和运行维护。一个可用于知识检索的记录通常至少包含：

```json
{
  "chunk_id": "policy-2026-07#section-4#chunk-2",
  "vector": "<embedding>",
  "text": "报销申请应在费用发生后……",
  "document_id": "policy-2026-07",
  "title": "差旅报销制度 / 提交期限",
  "source_uri": "docs/policy-2026-07.pdf",
  "page": 12,
  "tenant_id": "tenant-a",
  "acl": ["finance", "employee"],
  "valid_from": "2026-07-01",
  "embedding_model": "embedding-model@v3",
  "content_hash": "sha256:..."
}
```

因此，一个完整的向量存储层通常需要：

- 向量及原文、来源、版本、权限等元数据的持久化。
- 精确或近似近邻索引，以及相似度度量和 Top-K 查询。
- 在向量搜索前或搜索过程中应用租户、ACL、时间、语言等过滤条件。
- 新增、更新、删除、备份、扩缩容和索引重建能力。
- 稠密向量、稀疏关键词或全文检索的组合，以及结果融合。
- 延迟、召回率、过滤命中率、索引新鲜度和资源占用的监控。

专用向量数据库不是唯一选择。已有关系数据库或搜索引擎支持向量字段和 ANN 索引时，如果数据规模、过滤和可用性要求能够满足，继续使用现有系统往往更简单。Faiss 这类库则更接近向量索引工具：它适合在应用中构建高性能相似度搜索，但租户隔离、元数据事务、备份和服务治理仍要由外围系统承担。

### 为什么以前很少听到“向量数据库”

很多开发者的学习路径是：先学关系型数据库，后来接触 MongoDB、Redis 等 NoSQL，直到生成式 AI 流行后才第一次听到向量数据库。这个经历并不说明向量检索刚刚诞生，而是反映了两条时间线没有同步发生：**近邻搜索算法很早，面向普通应用开发者的专用向量数据库产品类别相对较新。**

如果把“向量数据库很早就存在”理解成“计算机很早就在存储多维数据、执行相似度和最近邻查询”，这个说法是成立的；如果理解成“几十年前就已经有今天这种带 collection、metadata filter、分片、副本和云 API 的独立向量数据库”，则会混淆算法、索引库与完整 DBMS。

| 阶段 | 代表性进展 | 当时更常见的使用方式 |
|---|---|---|
| 1970 年代 | 1975 年的 k-d tree 研究多维空间中的关联查找 | 计算几何、空间数据和较低维近邻查询中的数据结构 |
| 1990 年代 | 高维“维度灾难”推动 ANN；1998 年的 LSH 用局部敏感哈希近似查找近邻 | 算法论文和特定检索系统，而不是通用业务数据库 |
| 2000 年代至 2010 年代初 | 图片、音频、推荐和搜索系统大量使用特征向量；2011 年 Product Quantization 用短编码降低高维检索成本 | 机器学习或搜索团队维护离线索引、内部服务和专用库 |
| 2016—2017 年 | HNSW 提供高召回的图式 ANN；Faiss 把精确、近似、量化和 GPU 相似度搜索组合成工程库 | 大型平台和算法团队更容易构建十亿级向量检索，但数据库能力仍需外围系统补齐 |
| 2021—2022 年 | Milvus 的 SIGMOD 论文讨论 purpose-built vector data management system；Manu 的 VLDB 论文进一步讨论 WAL、可调一致性和计算存储分离 | “向量数据库管理系统”开始形成更清晰的研究与产品边界 |
| 2022 年以后生成式 AI 普及阶段 | 通用 embedding、RAG 和多模态模型让文本、图片、代码都能进入相似度检索链路 | 向量检索从少数推荐/搜索团队的基础设施变成大量应用开发者直接使用的组件 |

#### 为什么大模型流行前存在感较低

第一，过去的向量往往来自专用特征工程或垂直模型。图片检索团队保存视觉特征，推荐团队保存用户和商品向量，风控团队保存行为特征；普通 CRUD 应用不需要直接接触这些内部表示。

第二，很多系统把向量能力藏在产品后面。用户可以使用“相似图片”“猜你喜欢”“以图搜图”和语音指纹，却不会看到后端的特征向量、ANN 索引和召回服务。它更像搜索或机器学习基础设施，而不是每位 Web 开发者都要学习的数据库。

第三，早期工作负载常是批量生成特征、离线建索引、在线只读查询。团队可以把 Faiss 一类索引库包成内部服务。随着知识库需要持续新增、修改和删除文档，还要支持租户、ACL、备份、审计和水平扩缩，问题才从“怎样找近邻”升级为“怎样管理动态向量数据”。

第四，embedding 把不同非结构化数据统一成了相似接口。以前每个业务都要训练或选择专用特征；现在文本、图片、音频和代码都能通过预训练模型转成向量。RAG 又让大量开发者必须亲自处理切块、入库、过滤和检索，新产品类别因此迅速进入主流开发视野。

#### 它与关系型数据库、文档数据库是什么关系

MongoDB 这类文档数据库首先改变了逻辑数据模型：应用可以围绕嵌套文档组织和查询数据。向量数据库更突出的变化是**查询语义**：传统数据库擅长判断“是否相等、是否在范围内、怎样 JOIN”，向量检索则回答“谁最相似”，并返回带距离或相似度分数的排序结果。

| 系统视角 | 主要记录形态 | 典型查询 | 结果语义 |
|---|---|---|---|
| 关系型数据库 | 行、列、主外键和约束 | 等值、范围、聚合、JOIN、事务 | 满足确定条件的记录集合 |
| 文档数据库 | JSON/BSON 等嵌套文档 | 字段、数组、嵌套路径与聚合 | 满足文档条件的记录集合 |
| 向量检索系统 | 向量 + ID + 原文/metadata | 距离度量、Top-K、过滤和可选混合检索 | 按近似相关程度排序的候选集合 |

这三者不是严格互斥的数据库世代。PostgreSQL 可以通过 pgvector 增加向量查询，MongoDB、Elasticsearch、Redis 等现有系统也可以增加向量字段或索引；专用向量数据库同样会保存类似文档的 payload，并建立标量或倒排索引。更准确的问题不是“向量数据库会不会取代关系型或 NoSQL”，而是“当前查询是否需要把高维相似度作为一级能力，以及现有系统能否在过滤、更新、规模和可靠性目标下做好它”。

### 向量数据库内部怎样工作

向量数据库看起来在执行一条简单的 `search(vector, top_k, filter)`，内部却同时经过存储、索引和分布式查询链路。不同产品实现并不完全相同，但常见设计可以抽象为写入路径、读取路径和后台维护三部分。

#### 写入路径：先保证可恢复，再让数据可搜索

一条记录到达数据库后，常见步骤如下：

```text
鉴权与校验
  → 确认 collection / namespace、向量维度、距离函数和字段类型
  → 写入 WAL 或其他持久化日志
  → 更新可变 segment、memtable 或增量索引
  → 返回写入确认
  → 后台生成不可变 segment 与 ANN 索引
  → 发布新索引版本
```

WAL（Write-Ahead Log，预写日志）的核心思想是先记录“准备做什么”，再修改主要数据结构。服务异常退出后，可以重放日志恢复已经确认的写入。为了避免每插入一个向量都重建大型索引，许多系统会先把新数据写入可变区域，达到一定条件后封装成不可变 segment，再在后台构建索引。

这会带来一个容易忽略的问题：**写入成功、持久化成功和可以被 ANN 查询看见，未必是同一时刻。** 有的系统同步更新索引，有的系统异步索引；分布式系统还可能让副本稍后才看见新数据。因此测试不能只检查 API 返回成功，还要测 `write-to-search latency`：从写入确认到满足指定一致性要求的查询能够找到它，究竟需要多久。

更新通常可以理解为“为同一个逻辑 ID 写入新版本”。删除也可能先写 tombstone（删除标记），让查询立即忽略旧记录，再由 compaction（压实）在后台回收 segment 中的旧版本、已删除向量和无效索引空间。删除接口返回成功不代表所有副本、缓存、快照和备份中的物理字节已经同时消失；涉及隐私和合规时，必须单独定义删除传播与备份到期策略。

#### 读取路径：过滤、分片召回与全局合并

一次分布式向量查询可以概括为：

```text
身份与租户边界
  → 解析结构化过滤条件
  → 把查询路由到相关 shard
  → 各 shard 在活跃数据和多个 segment 中执行精确搜索或 ANN
  → shard 内合并候选
  → coordinator 合并全局 Top-K
  → 读取原文与元数据
  → 可选的融合、重排与权限复核
  → 返回结果、分数和来源
```

shard（分片）负责把不同记录分散到多台机器或多个逻辑分区，从而扩展容量与吞吐；replica（副本）保存同一份数据的冗余拷贝，用于容错和扩展读取。分片与副本不是一回事：增加分片改变数据分布和查询扇出，增加副本主要改变可用性与读能力。

查询通常要从每个相关分片多取一些局部候选，再合并成全局 Top-K。候选取得太少可能损失召回，取得太多则增加网络、CPU 和尾延迟。ANN 本身又具有近似性，所以“单机 Recall@10 很高”不等于经过分片、过滤和超时后的端到端 Recall@10 仍然相同。

过滤条件放在哪里会直接影响结果。预过滤先缩小合法候选，再做向量搜索；搜索中联合过滤会在索引遍历时同时考虑条件；后过滤先取近邻再删除不符合条件的记录。后过滤容易返回不足 $k$ 条，严格权限场景还不能让无权原文进入下游。各产品对过滤和 ANN 的组合方式不同，这往往比“是否支持 metadata filter”这个勾选项更重要。

#### 后台维护：索引不是一次性文件

数据库还要持续执行 segment 合并、索引构建、tombstone 清理、缓存淘汰、快照、备份和副本修复。后台任务会与在线查询争夺 CPU、内存、磁盘带宽和网络，因此压测应同时覆盖稳定查询、批量导入、持续更新、大量删除和节点恢复，而不能只测一个静态只读索引。

部分分布式向量数据库采用计算与存储分离：原始数据、日志和索引文件放在对象存储，查询节点把热点索引或数据缓存到内存和本地 SSD。这样可以独立扩缩计算和存储，但会引入缓存冷启动、对象存储读取和后台物化的延迟。另一些产品更依赖本地磁盘或内存，以更直接的资源模型换取较少的分布式组件。架构没有绝对优劣，要看工作负载是内存敏感、延迟敏感、写入密集，还是容量和弹性优先。

### 常见向量数据库与相关方案

下面的对比基于 2026-07-28 的官方文档，只描述稳定定位，不代表性能排行榜。开源产品通常也提供托管版本，云服务也可能持续增加索引和混合检索能力；真正选型前仍需核对目标版本。

| 方案 | 定位与检索基础 | 优先考虑它的情形 | 主要注意点 |
|---|---|---|---|
| **pgvector** | PostgreSQL 扩展；支持精确搜索、HNSW 和 IVFFlat，可直接使用 SQL、事务、JOIN 与 PostgreSQL 索引 | 业务事实、ACL 和向量已经适合放在 PostgreSQL；团队希望少引入一个系统 | ANN 与复杂过滤会受到查询计划和候选扫描影响；大规模分片与向量专用调优仍依赖 PostgreSQL 周边方案 |
| **MongoDB Vector Search** | 在文档数据库旁建立独立向量搜索索引；可以在 BSON 文档及其他字段旁保存 embedding，并通过聚合管道执行 ANN/ENN 与预过滤 | 业务数据已经以 MongoDB 文档为事实源，希望在同一数据平台加入语义搜索 | 向量搜索索引与普通数据库索引并非同一结构；支持范围、部署形态和管道组合随版本变化，需核对目标环境并测试索引新鲜度 |
| **Elasticsearch / OpenSearch** | 分布式搜索引擎增加向量字段与 kNN；关键词、过滤、聚合、地理和混合检索是其原生搜索语境 | 已有搜索集群，或者产品强依赖 BM25、分词、同义词、facet 和语义信号融合 | 集群资源和相关性调优面较广；两个项目的版本、引擎、过滤语义和 API 已经分化，不能当成完全相同的产品 |
| **Qdrant** | 专用向量搜索引擎；以 HNSW、payload、payload index、segment 和 WAL 为核心，并支持磁盘存储与分布式部署 | 需要自托管、结构化过滤与向量搜索紧密结合，希望系统边界保持专注 | 过滤字段是否建 payload index 会显著影响行为；应验证 segment 优化、磁盘模式、复制与重分片期间的尾延迟 |
| **Weaviate** | 对象与向量数据库；向量索引与倒排索引并存，提供 HNSW、Flat、Dynamic 等索引形态和混合检索 | 希望以 collection/object 组织语义数据，并使用集成式向量化、关键词与向量检索 | 索引形态、同步/异步索引和多租户配置会改变内存、新鲜度与运维方式；内置向量化也要锁定模型版本 |
| **Milvus** | 面向分布式向量检索的数据库；计算与存储可分离，支持 HNSW、IVF 系列、DiskANN 等多种索引以及多级一致性 | 数据和吞吐需要水平扩展，团队希望细调索引、查询节点、存储和一致性 | 集群组件、依赖与参数更多；索引选择、数据装载、对象存储和一致性等级都需要专门容量规划 |
| **Pinecone** | 全托管向量数据库；serverless 架构以 namespace 隔离记录，提供 metadata filtering，并分离读写路径 | 希望减少集群部署、升级、扩缩容和索引运维，把重点放在应用检索质量 | 底层索引和资源控制不如自托管方案直接；应验证数据驻留、配额、成本模型、导入方式、可观测性和迁移出口 |
| **Redis** | 通用实时数据平台中的向量二级索引；向量、JSON/hash 元数据和其他 Redis 数据结构可放在同一系统 | 已使用 Redis 维护在线状态或特征，并需要低延迟的向量与结构化查询组合 | 不能因 Redis 很快就忽略数据常驻层级、索引内存、持久化、复制和故障恢复成本；应按真实数据量做容量测试 |
| **Chroma** | 从嵌入式本地库、单节点到分布式/云的向量数据平台；collection 保存 ID、向量、文档和 metadata | 教学、原型和本地开发需要低门槛起步，或希望同一 API 逐步尝试服务化 | 本地、单节点和分布式模式的存储架构与能力可能不同；进入生产前要重新验证 HA、备份、权限、并发和迁移路径 |

Faiss 没有列为数据库，因为它主要提供向量索引与搜索算法。它非常适合做本地精确基线、离线批处理和自定义检索服务，但不会自动提供完整的文档事务、租户鉴权、网络服务、备份恢复和运维控制面。

这张表也说明“专用向量数据库”不是天然高于“带向量能力的现有数据库”。如果核心查询是 `tenant_id + product_id + 时间范围 + 向量相似度`，关系数据库的事务和复合条件可能更重要；如果核心是关键词、facet、同义词和语义结果融合，搜索引擎更自然；只有当向量规模、索引控制、过滤召回或独立扩缩成为主要矛盾时，专用系统的价值才会明显。

### 同名功能为什么不能只看勾选表

几乎所有产品都可以宣称支持“向量搜索、过滤、分布式和混合检索”，但这些词背后的语义可能不同：

- **过滤**：是在 ANN 前、遍历中还是 Top-K 后执行？严格过滤时能否稳定返回足够候选？
- **新鲜度**：写入确认后是否立即可搜索？同一 session 能否读到自己的写入？索引积压怎样观测？
- **删除**：查询何时不可见，物理空间何时回收，删除怎样传播到副本、缓存、快照和备份？
- **混合检索**：是在数据库内统一执行 BM25 与向量搜索，还是客户端分别查询再融合？分数怎样归一化？
- **多向量**：一条记录能否保存标题、正文、图片等多个命名向量，并分别设置度量和索引？
- **多租户**：是逻辑字段过滤、namespace、独立 collection，还是物理 shard？能否防止 noisy neighbor？
- **一致性**：提供强一致、session、bounded staleness 还是 eventual consistency？故障切换后保证是否变化？
- **资源模型**：原始向量、量化表示、图边、payload 和全文索引分别位于内存、本地 SSD 还是对象存储？
- **可运维性**：是否支持在线备份恢复、滚动升级、限流、审计、指标、索引迁移和容量预警？

因此，功能表适合生成候选名单，不适合直接做最终决策。最终要把“支持”改写成可测试的验收条件，例如：“用户写入后 2 秒内，在同一租户查询中可见”“ACL 过滤后 Recall@10 不低于已标注基线”“删除后在线查询立即不可见，并在既定保留期后从备份过期”。

### 一套更可靠的选型顺序

第一步不是下载所有向量数据库跑默认 benchmark，而是先确认是否已有合适的事实存储或搜索系统：

1. 已有 PostgreSQL，向量查询必须和事务数据、ACL、状态或复杂 JOIN 保持一致：先用 pgvector 建立基线。
2. 业务数据已经是 MongoDB 文档，希望复用过滤和聚合链路：先验证 MongoDB Vector Search，避免为了向量复制出第二份事实源。
3. 已有 Elasticsearch/OpenSearch，而且关键词、筛选、聚合和语义搜索必须统一：先验证现有搜索引擎的向量与混合检索。
4. 需要专用的过滤向量服务并希望自托管：比较 Qdrant、Weaviate 等专用系统在真实过滤分布下的表现。
5. 数据、吞吐或索引类型要求需要独立水平扩展：评估 Milvus 一类分布式架构，同时计算运维复杂度。
6. 团队不希望管理集群：比较 Pinecone 及其他产品的托管版本，重点核对成本、驻留、配额和退出方案。
7. 已有 Redis 且检索属于低延迟在线数据路径：验证 Redis 向量索引能否满足容量和持久化要求。
8. 只是教学或原型：Chroma、Faiss 或本地精确搜索通常足以开始，但要提前记录迁移所需的数据模型与评测集。

然后用同一套数据和查询做 POC。测试集应包含常见问题、难负例、严格过滤、空结果、刚写入、刚删除、热点租户和超长 payload。除了 Recall@k 与 p95/p99 延迟，还要记录写入到可搜索延迟、索引构建时间、持续更新吞吐、删除后的磁盘回收、节点故障恢复、备份还原时间、峰值内存、网络与存储成本。只有这些指标同时进入报告，产品对比才从“API 试用”变成数据库选型。

### HNSW：在分层近邻图中导航

HNSW（Hierarchical Navigable Small World）是常见的图式 ANN 索引。可以把它理解为“高速公路 + 地方道路”：上层图稀疏，适合跨越较远区域；下层图更密，适合在候选附近细查。搜索从上层入口开始，沿着更接近查询向量的邻居移动，再逐层下降到最底层。

```text
第 2 层（稀疏）:  A ─────────── F ─────────── K
                  │             │             │
第 1 层（中等）:  A ── C ── E ── F ── H ── J ── K
                  │  ╱ ╲  │  ╱ ╲  │  ╱ ╲  │
第 0 层（密集）:  A-B-C-D-E-F-G-H-I-J-K-L-M
```

HNSW 通常能在较低延迟下取得较高召回，但需要额外保存图连接。邻接数、构建时搜索深度和查询时搜索深度都会影响内存、建库时间、延迟与召回。参数越大并非总是越好，最终要在目标数据分布上绘制“召回率—延迟—内存”曲线。

### IVF 与 PQ：先缩小范围，再压缩向量

IVF（Inverted File Index）先把向量空间聚成多个区域，并把向量放入对应倒排表。查询时先找到较近的若干区域，只扫描这些区域中的候选。探测区域越多，越可能找回真正近邻，但计算量也越大。

PQ（Product Quantization，乘积量化）把高维向量分成多个子向量，分别用有限码本近似，再用短编码代替原始浮点向量。它可以显著降低存储和距离计算成本，但会引入量化误差。IVF 与 PQ 经常组合：前者减少需要扫描的候选，后者压缩候选表示；有些系统还会对候选使用原始向量或更高精度表示做二次精排。

| 索引思路 | 主要优势 | 主要代价 | 适合先验证的情形 |
|---|---|---|---|
| Flat / 精确搜索 | 结果精确、实现简单、适合作为基线 | 计算量随数据规模增长 | 数据较小、批处理、质量基准 |
| HNSW | 查询延迟低、召回与延迟可调 | 图结构占内存，构建和删除策略需评估 | 内存较充足、在线低延迟检索 |
| IVF / IVFFlat | 只扫描部分区域，搜索范围可调 | 需要训练聚类，数据漂移后可能重建 | 数据规模较大、希望控制扫描量 |
| PQ / IVFPQ | 显著压缩向量，降低内存和带宽 | 存在量化误差，参数与训练较复杂 | 内存敏感或大规模候选检索 |

表中的选择不是产品排行榜。同一种索引在不同语言、向量维度、数据分布、过滤比例和硬件上可能表现完全不同。选型时至少应使用真实查询集测量 Recall@k、p50/p95 延迟、吞吐、内存、建库时间、更新延迟和过滤后的召回率。

### 元数据过滤必须进入检索边界

相似度只回答“内容像不像”，不回答“用户能不能看”“文档是否仍然有效”。例如一个员工只能访问本部门制度，检索必须把 `tenant_id`、ACL 和有效期作为硬条件。先从全库召回 100 条再在应用层删掉无权结果，会造成两个问题：候选可能全部被删光，而且未经授权的数据已经穿过了不该穿过的系统边界。

过滤和 ANN 的组合并不总是简单。先过滤后搜索可能让候选集合很小；在图搜索中边走边过滤可能破坏图的连通性；先搜索后扩大候选再过滤则要严格保证原文不会泄露。数据库的过滤策略、过滤字段索引和最坏情况延迟都应进入压测，而不只验证“接口能返回结果”。

### 从向量召回到混合检索和重排

稠密向量擅长语义近似，但产品编号、错误码、人名、日期和精确短语往往更适合关键词或结构化过滤。常见生产链路会并行执行稠密向量检索和 BM25 等稀疏检索，再用归一化分数、加权融合或 Reciprocal Rank Fusion 合并候选。

初次召回追求的是“不要漏掉证据”，因此通常快而粗。重排器再对较小的候选集合做更精细判断。双编码器分别编码 query 与文档，适合大规模召回；Cross-Encoder 把 query 和候选一起编码，能观察词级交互，但每个候选都要单独计算，适合第二阶段。

```text
稠密向量召回 ─┐
关键词召回   ──┼→ 去重与融合 → 元数据/权限检查 → 重排 → 上下文候选
业务规则召回 ─┘
```

重排不是任何系统都必须增加的固定步骤。如果初始检索已经满足质量和延迟目标，额外模型只会增加复杂度；当相关证据经常能召回但排序靠后，或者问题与文档需要细粒度匹配时，重排才更有价值。

### 数据入库与更新也是检索的一部分

一条可靠的离线链路不仅计算向量，还要维护文档身份和版本：

```text
连接数据源 → 解析/OCR → 清洗与去重 → 按结构切块
          → 生成稳定 chunk_id → 写入原文和元数据
          → 计算 embedding → 构建稀疏与向量索引
          → 质量抽检 → 发布索引版本
```

切块太大时，一个向量会混合多个主题；切块太小时，答案和限定条件可能被拆开。固定长度加重叠便于起步，按标题、段落、列表和表格切分通常更能保留结构。还可以采用父子块：用小块检索，用包含标题和邻近段落的父块交给模型。不存在适合所有文档的固定字符数，应通过真实问题和证据标注调参。

更新时不能只追加新向量。系统要处理内容修改、删除、权限变化、embedding 模型升级和重复块。常见做法是保存内容哈希和 embedding 版本，用新索引做影子构建和离线评测，通过后再切换别名；删除则要同时覆盖原文、向量索引、缓存和备份策略，避免“文档删了但旧向量还能搜到”。

用 sentence-transformers 可以先建立一个不带 ANN 的精确检索基线：

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('BAAI/bge-small-zh-v1.5')

docs = [
  "Transformer 使用自注意力机制处理序列",
  "梯度下降是优化神经网络的基本方法",
  "向量数据库支持高效的相似度搜索",
]
query = "如何搜索相似的向量？"

doc_embeds = model.encode(docs)
query_embed = model.encode(query)

similarities = model.similarity(query_embed, doc_embeds)[0]
best = int(similarities.argmax())
print(f"最相关: {docs[best]} (相似度 {similarities[best]:.3f})")
# 最相关: 向量数据库支持高效的相似度搜索 (相似度 0.82)
```

这个例子没有数据库、过滤和索引，价值恰恰在于提供可解释基线。加入 ANN、混合检索或重排后，应和它在同一组标注查询上比较，而不是只看新方案更快。

### 对比学习：Embedding 是怎么训练的

前面说了"embedding 是训练出来的"，但具体怎么训练？最核心的方法叫**对比学习**。

对比学习可以用一句话概括：**把正例拉近、把负例推远**。

假设我们有一组配对数据（问题, 相关文档）。对于每个问题，对比学习的目标是：
- 正例：和这个问题相关的文档，它们的向量应该尽量接近
- 负例：和这个问题无关的文档，它们的向量应该尽量远离

常见损失函数是 InfoNCE。思路是：在一个 batch 中，给定一个 query，只有 1 个正例文档，其余都是负例。模型需要从所有候选中把正例"点出来"。用公式表达：

```
loss = -log( exp(sim(q, d+)) / Σ exp(sim(q, di)) )
```

其中 q 是 query 向量，d+ 是正例文档向量，di 是 batch 中所有文档（含正例和负例），sim 是相似度。这个损失鼓励正例得分远高于负例。

但负例的选择很有讲究。随机选的负例太容易区分（"苹果"和"量子力学"明显无关），模型学不到东西。好的做法是用 **Hard Negative Mining**：故意选那些看起来有点相关但实际不相关的文档做负例。比如对于"Python 如何读 JSON 文件"，选"JavaScript 如何读 JSON 文件"做负例——话题相似但答案不同，模型必须区分更细的语义差异。

CLIP 的训练也是一种对比学习，只是正例是图片-文字对：一张猫的图片和"一只猫"这段文字是正例，和"一辆汽车"是负例。训练后，图片和文字共享一个向量空间，支持跨模态检索。

理解对比学习后，你会知道为什么 embedding 模型对训练数据分布敏感：如果训练数据里没有你的领域数据，模型学不到你这个领域的语义关系。这也是为什么通用 embedding 模型在法律、医疗等垂直领域往往需要微调。

## Embedding 在系统中的常见用途

Embedding 不只用于 RAG。推荐系统会用用户 embedding 和商品 embedding 计算匹配程度；广告系统会用向量表示用户兴趣和广告内容；代码搜索可以把自然语言问题和代码片段映射到同一空间；异常检测可以寻找远离常见样本分布的点。

例如客服系统可以把历史工单都转成 embedding。当新问题出现时，系统先找到语义最接近的历史工单，看看过去如何处理。这样即使用户说法不同，也能复用历史经验。

再比如产品分析中，可以把用户行为序列表示成 embedding。相似行为模式的用户会靠近，系统就可以发现“经常浏览但很少下单”的用户群，或者识别行为突然偏离常态的异常账号。

## 动手试试

准备 10 条公司制度、产品说明或个人笔记，每条控制在一小段。用任意 embedding 工具把它们转成向量，再输入 2-3 个自然语言问题，观察最相似的文档块是否真的相关。

如果暂时不写代码，也可以手工设计切块方案：哪些内容应该按标题切，哪些段落需要保留上下文，哪些元数据必须保存。这个练习能帮助你理解 RAG 的关键不只是“调用 embedding 模型”，还包括切块、元数据、召回和验证。

## 小结

Embedding 把离散世界转化为连续向量空间，是语义搜索、推荐、RAG、多模态对齐和表征学习的基础。它是模型根据训练目标学出的关系空间，而非手工定义的编号。向量索引负责加速近邻搜索，向量数据库还要管理原文、过滤、更新和运维；完整 RAG 则在检索之外继续处理证据组装、生成、引用和评测。

理解 embedding 后，再看 Transformer 和大语言模型中的 token 表示，就能更容易把抽象概念落到实际系统：token 先变成向量，向量在多层网络中不断被上下文改写，最终支持理解、生成、检索和推理。
