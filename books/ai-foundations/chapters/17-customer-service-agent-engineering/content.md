# 客服 Agent 工程化实战

> **更新时间**：2026-07-30
>
> **事实审校**：分层意图路由、上下文状态、RAG、工具安全与评测方法依据经典文本分类、检索和生产系统资料复核；文中的延迟、流量占比和阈值均为设计示例，正式上线必须以本地数据校准。

一家销售手机、耳机和家用电器的公司准备上线智能客服。用户可能询问产品差异、活动规则、物流进度、退换货条件、保修方式，也可能要求取消订单、创建退货单或转接人工。最直接的实现是把每条消息连同全部聊天记录交给一个大语言模型，再让它决定如何回答和调用工具。

这个原型很快就会遇到问题。即使用户只输入“查物流”，系统也要等待大模型推理；用户量增长后，每轮都携带历史对话会不断消耗 token；模型还可能把“先别取消，我只想问能不能退”错误理解为立即取消。客服系统不仅要“听懂”，还要快、便宜、稳定、可审计，并且不能因为一句模糊表达就执行不可逆操作。

解决办法不是为所有请求寻找一个更大的模型，而是把客服拆成一条分层处理链：确定性规则先处理高置信、低变化的输入；小模型承担大部分语义分类；只有歧义、多意图、长文本和未知请求才进入大模型；最终业务动作仍由状态机、权限系统和业务工具控制。本章从这个实际问题出发，设计一套可以逐步上线的客服 Agent。

## 先定义系统到底要完成什么

“做一个智能客服”不是可执行需求。团队需要先列出服务边界、风险等级和成功条件，否则意图分类再准确也不知道应把用户送到哪里。

一个电商客服可以先定义下面的业务域：

| 业务域 | 典型请求 | 处理方式 | 风险 |
|---|---|---|---|
| 产品咨询 | “这两款耳机有什么区别” | 检索产品资料并生成说明 | 低 |
| 售前政策 | “学生有优惠吗” | 检索活动规则，标注适用时间和地区 | 低 |
| 订单查询 | “我的订单发货了吗” | 鉴权后读取订单系统 | 中 |
| 物流查询 | “快递到哪里了” | 读取物流接口 | 中 |
| 退换货咨询 | “拆封后还能退吗” | 检索政策并调用资格预检 | 中 |
| 取消、退款、退货 | “帮我取消第二件商品” | 进入有确认和幂等控制的写流程 | 高 |
| 投诉与人工服务 | “我要投诉，转人工” | 建工单或转接人工 | 中到高 |
| 闲聊与未知请求 | “你会写代码吗” | 简短回答、澄清或拒绝 | 低 |

意图不是为了给句子贴一个漂亮标签，而是为了选择下一条受控路径。若 `refund_policy` 和 `create_refund` 最终需要不同权限、不同确认和不同工具，它们就不应合并成一个含糊的“退款”意图。反过来，如果“快递在哪”和“查物流”进入完全相同的流程，就没有必要为了措辞差异建立两个标签。

在设计标签前，先回答四个问题：用户想知道信息，还是改变外部状态？需要哪些已验证的实体和身份？错误执行的后果是什么？系统应该回答、追问、调用工具还是转人工？这些问题决定路由体系，而不是模型本身。

## 一套可上线的总体架构

客服 Agent 可以拆成九个相互约束的部分：

```text
用户渠道
  -> 接入层：鉴权、限流、去重、文本规范化
  -> 会话层：thread、当前流程、已确认实体、待补槽位
  -> 分层路由：安全规则 -> 业务规则 -> 小模型 -> 大模型兜底
  -> 对话控制器：状态机、澄清、任务分解、停止条件
  -> 知识层：产品资料、售后政策、FAQ、RAG
  -> 工具层：订单、物流、资格判断、取消、退款、工单
  -> 回复层：模板、结构化数据渲染、受证据约束的生成
  -> 安全层：权限、确认、幂等、审计、隐私保护
  -> 观测层：trace、延迟、token、路由结果、业务终态
```

大模型只是分层路由和复杂回复中的一个组件。会话状态不应只存在于 prompt，退款资格也不应让模型根据一段政策文字自行计算。Agent harness 负责把每次请求放入状态机，给模型有限上下文，调用受约束工具，保存检查点，并在失败或人工接管后继续。

## 为什么不能把所有输入都直接交给大模型

### 响应时间会被最慢路径支配

“转人工”“查订单”和“你好”本来可以在几十毫秒级完成路由。如果它们都先经过生成模型，系统会增加排队、首 token 和结构化解析时间。平均延迟看起来可能还能接受，但促销期间的并发会放大队列，真正影响体验的是 p95 和 p99 尾延迟。

### token 成本会随流量和历史一起增长

一次请求的期望模型成本可以写成：

```text
期望成本 = Σ(某条路由的流量占比 × 该路由平均调用成本)
```

如果所有请求都调用大模型，流量占比就是 100%。如果规则处理 35%、小模型处理 50%、大模型只处理 15%，大模型成本只落在最后一个分支。这里的比例只是示例，真实比例必须从业务日志测量，不能先认定“正则一定覆盖大部分”。

历史对话也会增加输入 token。把 30 轮聊天原样重复发送，既昂贵，也会让已经失效的信息干扰判断。生产系统应保存结构化状态，只选择当前任务需要的最近消息、摘要和工具事实。

### 生成能力不等于业务控制能力

大模型可以理解“我不想退了”的语义，却不应该直接获得退款权限。它可能误解否定范围、混淆多个订单、引用过期政策，或在工具超时后重复提交。路由模型可以提出候选意图，真正的写操作仍需要身份、对象、金额、业务资格、用户确认和幂等键。

因此，系统优化的目标不是消灭大模型，而是让每类请求进入与其复杂度和风险匹配的最短可靠路径。

## 第一层：确定性预处理和规则路由

规则适合处理边界清晰、表达稳定、需要高精度的输入。例如菜单编号、固定指令、订单号、明确的“转人工”，以及对写操作有直接影响的否定表达。它的价值是快、便宜、可解释，但前提是只在自己擅长的范围内做决定。

### 先规范化，再匹配

进入规则前可以完成：

- Unicode 和全半角规范化，折叠无意义空白。
- 保留原文的同时生成匹配文本，不要因清洗丢掉证据。
- 识别渠道按钮、菜单编号和系统事件，它们比自由文本更可靠。
- 提取订单号、商品编号、时间、金额等候选实体，并对敏感字段脱敏。
- 检测重复消息、重放请求、超长文本和异常频率。
- 将语音识别置信度、图片 OCR 来源等通道信息一并带入路由。

文本规范化不能粗暴删除“不、别、没、取消”等词。这些词恰恰决定用户是否授权某个动作。

### 规则应追求高精度，而不是假装理解所有语言

下面这些输入适合直接命中规则：

```text
“转人工”                 -> handoff_human
“1” + 当前菜单为售后       -> after_sales_menu
“查订单 A20260730001”     -> order_status + order_id
“不要取消订单”            -> negated(cancel_order)
```

“苹果坏了”却不能仅凭“苹果”路由到手机售后，因为它也可能指水果；“退一下”也可能是退出页面、退订服务或退货。规则命中应附带证据、作用域和置信等级，未满足条件就继续交给下一层，而不是强行返回结果。

一种比大量散落 `if` 更易维护的结果结构如下：

```json
{
  "matched": true,
  "candidate_intents": ["refund_policy"],
  "negated_intents": ["cancel_order"],
  "entities": {"order_id": "A20260730001"},
  "evidence_spans": ["先别取消", "现在退要不要运费"],
  "rule_version": "router-rules-2026-07-30",
  "decision": "continue_to_small_model"
}
```

规则可以产生候选和约束，不一定要独立完成最终分类。

## 否定信息：知道用户不要系统做什么

否定识别对客服尤其重要。下面四句话都出现“取消”，授权含义却完全不同：

```text
帮我取消订单。
不要取消订单。
如果取消订单，要手续费吗？
我说的是取消提醒，不是取消订单。
```

只做关键词计数会把它们全部路由到取消流程。更可靠的处理要区分：

- **肯定动作**：用户明确要求执行。
- **否定动作**：用户明确禁止执行。
- **假设咨询**：用户询问“如果做会怎样”，没有授权执行。
- **纠正或引用**：用户在纠正系统，或复述别人说过的话。

简单场景可以使用否定词表加窗口规则，例如在动作词前后限定范围内查找“不、别、无需、暂时不要”。但中文否定范围可能跨越分句，“不是不想退，是还没决定”还包含双重否定。规则层应以高精度识别明确样本，并把复杂样本交给上下文模型。

更重要的是，否定结果必须进入执行策略。即使后续小模型给 `cancel_order` 较高分，只要当前消息包含高置信的 `negated(cancel_order)`，系统就不能进入取消工具；它可以解释政策或追问，但不能把否定当成一个普通特征后任由模型覆盖。

## 第二层：用小模型承担主要语义路由

规则无法枚举“我的包裹还在路上吗”“为什么一直没派送”“快递是不是丢了”这些语义近似但措辞不同的表达。让大模型处理当然可以，但意图集合通常只有几十到几百个，使用专门的小模型会更快、更便宜，也更容易稳定部署。

### 三类常见实现

| 方法 | 输入表示 | 优点 | 局限 | 适合阶段 |
|---|---|---|---|---|
| TF-IDF + 线性分类器 | 字符或词 n-gram | 训练快、CPU 友好、基线清楚 | 上下文和语义泛化较弱 | 冷启动基线 |
| fastText 类分类器 | 词和子词向量 | 轻量，对拼写和词形变化较稳健 | 复杂语境能力有限 | 高频固定意图 |
| 小型 Transformer 分类器 | 上下文编码 | 能处理语序、否定和语义近似 | 需要标注、推理和校准 | 主要生产路由 |
| Embedding + 原型/近邻 | 句向量与样例向量 | 新意图可快速加样例，便于解释 | 阈值和边界容易漂移 | 长尾和快速迭代 |

实践中可以同时保留一个线性基线和一个小型编码器。复杂方案必须证明它在关键切片、延迟和维护成本上优于基线，而不是只看总体 Accuracy。

### 不要只输出一个标签

客服输入经常包含多个意图，例如“查一下物流，到了以后怎么退”。路由器最好输出多标签、实体、排序分数和不确定性：

```json
{
  "intents": [
    {"name": "logistics_status", "score": 0.91},
    {"name": "refund_policy", "score": 0.78}
  ],
  "entities": {"order_ref": "current_order"},
  "out_of_scope_score": 0.04,
  "top_margin": 0.13,
  "model_version": "intent-small-v12"
}
```

最高分不等于可以执行。系统还要看分数是否经过校准、第一名和第二名差距、是否属于分布外输入，以及意图风险。对“产品颜色”分类错一次，最多答非所问；对“查询退款政策”和“立即退款”混淆，则可能产生真实损失。

### 阈值要按风险和数据校准

可以为不同意图设置不同门槛：

- 低风险知识问答在高置信时直接进入 RAG。
- 中等置信或前两名接近时进入澄清或大模型兜底。
- 写意图即使高置信，也只进入“准备动作”状态，不能跳过确认。
- 未知、越界和高风险投诉优先转人工。

Softmax 的 0.95 不是天然的“95% 会正确”。团队应在独立验证集上画可靠性曲线，使用温度缩放等方法做校准，并按渠道、语言、产品线和新老用户切片检查。阈值是发布配置的一部分，必须版本化。

## 第三层：大模型只处理真正需要语言推理的输入

大模型适合处理长投诉、隐含意图、多个约束、跨句指代、新出现的表达和小模型无法区分的边界样本。它是兜底和复杂解析器，而不是每条消息的默认入口。

送给大模型的输入也不应是“全部聊天记录 + 请判断意图”。更稳妥的请求包含：

- 允许使用的意图枚举和每个意图的执行含义。
- 当前消息、必要的最近轮次和结构化会话状态。
- 规则层发现的否定、实体和安全约束。
- 小模型 top-k 结果及其版本，不把分数描述成事实。
- 明确的 JSON schema、未知类别和“需要澄清”选项。
- 要求返回支持判断的原文片段，而不是隐藏思维链。

```json
{
  "primary_intent": "refund_policy",
  "secondary_intents": [],
  "dialogue_act": "ask_information",
  "negated_actions": ["cancel_order"],
  "required_slots": ["product_id", "purchase_channel"],
  "needs_clarification": false,
  "evidence_spans": ["先别取消", "退的话要运费吗"]
}
```

结构化结果先经过 schema 和策略校验，再交给对话控制器。大模型不能凭输出一个工具名就获得调用权限。若解析失败、标签不在枚举中或证据与结果冲突，系统应重试一次更严格的解析、转澄清或转人工，而不是猜测补全。

## 有些意图离开上下文根本无法判断

用户说“第二个呢”“还没到”“那就这样吧”，仅看当前文字几乎没有意义。直接拼接全部历史虽然简单，却会带来 token 增长、旧信息污染和隐私暴露。解决方法是把对话从纯文本日志变成可恢复的结构化状态。

### 会话状态至少保存什么

```json
{
  "thread_id": "t_123",
  "active_workflow": "return_consultation",
  "last_system_question": "您问的是订单中的主机还是滤芯？",
  "open_slots": ["line_item_id"],
  "confirmed_slots": {"order_id": "A20260730001"},
  "candidate_slots": {"line_item_id": ["item_main", "item_filter"]},
  "recent_intents": ["logistics_status", "refund_policy"],
  "negated_actions": ["cancel_order"],
  "tool_facts": {"order_status": "shipped"},
  "state_version": 18,
  "expires_at": "2026-07-30T13:00:00Z"
}
```

工具事实要带来源和时间，不能让一句旧的聊天摘要永久代表真实订单状态。写操作前必须重新读取关键状态。

### 用当前状态解释省略和指代

若系统刚问“主机还是滤芯”，用户回复“第二个”，对话控制器可以把它解析为 `item_filter`。若前一轮列出了两个订单，但之后又谈了另一个商品，“第二个”就可能歧义，系统应展示候选并追问。

小模型可以使用“结构化状态摘要 + 当前消息”作为一对输入，例如：

```text
[STATE] active=return_consultation; open_slot=line_item_id;
last_question=主机还是滤芯; candidates=主机|滤芯
[UTTERANCE] 第二个
```

规则也可以利用状态：当存在 `open_slot=line_item_id` 时，菜单编号和“第一个/第二个”的解释优先绑定到候选列表，而不是重新做全局意图分类。只有状态不完整、候选过多或表达冲突时才升级到大模型。

### 什么时候应该清空或切换上下文

用户说“换个问题”“说回刚才那个订单”或明确提供新订单号时，系统需要切换任务焦点。可以为流程设置 TTL，在长时间停顿后重新确认关键实体；同一用户从不同设备进入时，也不能仅凭模糊指代恢复高风险动作。

上下文继承遵循“最近、相关、已确认”原则。候选槽位不能当作已确认事实，旧的否定约束也要有作用范围。例如“这单先别取消”约束的是指定订单，不应阻止用户稍后取消另一单。

## 多意图不是简单选一个最高分

“查一下物流，到了以后怎么退”同时包含当前查询和未来咨询；“耳机不要了，手机壳继续发”包含不同商品上的相反动作。系统应把它们解析成带对象和语气的任务，而不是只选 `refund`。

一种任务表示如下：

```json
{
  "tasks": [
    {"intent": "logistics_status", "target": "order_main", "mode": "execute_read"},
    {"intent": "refund_policy", "target": "order_main", "mode": "answer_hypothetical"}
  ],
  "forbidden_tasks": [
    {"intent": "cancel_order", "target": "order_main"}
  ]
}
```

对话控制器再根据依赖排序：先确定订单，再并行读取物流和适用政策，最后组合回答。若两个任务都要改变状态，应分别展示对象和影响，让用户逐项确认。系统不应因为一句话包含多个动词就让大模型自由规划任意工具链。

## 产品介绍与售后知识：RAG 放在哪里

产品参数、兼容性、保修范围和退换货政策会变化，又需要向用户说明依据，适合使用 RAG。意图路由先确定知识域和实体，检索层再用这些条件缩小范围：

```text
query: “拆封后的 Pro X 耳机能退吗”
filters:
  product_id = pro_x
  region = CN
  sales_channel = official_store
  policy_status = active
  effective_at <= purchase_time
```

检索结果必须保留文档 ID、版本、有效时间和引用片段。生成器只能根据命中的证据回答，资料不足或政策冲突时应说明无法确认并转人工。

RAG 不应该承担实时订单查询。订单状态、库存、退款进度应来自业务 API；退款资格中可以变化的确定性规则，最好由政策服务或规则引擎计算。模型可以解释 `eligible=false, reason=opened_hygiene_product`，但不能自己从几段文档推断后直接拒绝用户。

对常见产品问题，可以缓存“规范化问题 + 产品版本 + 政策版本”的检索结果或已审核答案。政策一更新，缓存键中的版本也应改变或主动失效，避免低延迟换来旧答案。

## 工具层：查询和执行必须分开

客服至少会接入这些工具：

- `get_order`：读取订单、商品行和当前状态。
- `get_logistics`：读取承运方和轨迹。
- `check_return_eligibility`：由业务规则计算退货资格和费用。
- `prepare_cancellation`：生成取消预览，不立即提交。
- `commit_cancellation`：在确认和幂等约束下提交。
- `create_return_request`：创建退货申请。
- `create_support_ticket`：创建人工工单。
- `handoff_human`：把结构化摘要和证据交给人工座席。

高风险工具不应设计成一个宽泛的 `execute_action(type, payload)`。语义化工具能明确前置条件和权限。例如：

```json
{
  "name": "commit_cancellation",
  "input": {
    "order_id": "string",
    "line_item_ids": ["string"],
    "confirmation_token": "string",
    "idempotency_key": "string"
  },
  "preconditions": [
    "authenticated_user_owns_order",
    "items_are_cancellable",
    "confirmation_matches_preview",
    "request_not_previously_committed"
  ]
}
```

确认必须绑定准确对象、金额和影响，而不是问一句泛化的“是否确认”。用户确认的是“取消订单 A 的耳机，不取消手机壳”，系统就不能在确认后替换商品列表。

工具超时也不能盲目重试写操作。系统先用幂等键查询上一次是否成功，再决定继续、补偿或转人工。对话里显示“操作失败”之前，也应区分请求未发送、结果未知和业务明确拒绝。

## 回复不一定需要生成模型

工具返回结构化结果后，很多回复可以用模板完成：

```text
订单 {{order_id}} 已于 {{shipped_at}} 发货。
当前状态：{{status}}。
承运方：{{carrier}}，运单号尾号 {{tracking_suffix}}。
```

模板快、稳定、便于国际化，也能避免模型改写金额、日期和状态。产品对比、长投诉总结或多个证据的综合解释可以使用大模型，但应把不可改写字段以结构化方式锁定，并在输出后校验订单号、金额、链接和引用。

一个常见组合是：固定开头说明结果，中间用模型把证据组织成自然语言，结尾用固定按钮提供下一步。模型负责表达，不负责决定用户是否有资格退款。

## 延迟和成本如何系统优化

优化不是只换一个更快模型，而是缩短最常见路径，并让昂贵步骤按需发生。

| 优化点 | 做法 | 需要防范的问题 |
|---|---|---|
| 提前退出 | 菜单、明确规则和高置信小模型直接路由 | 错误的高置信短路 |
| 缩短上下文 | 使用结构化状态、最近相关轮次和按需检索 | 摘要丢失关键否定或确认 |
| 缓存 | 缓存静态 FAQ、检索结果和只读工具结果 | 版本失效、跨用户泄露 |
| 并行读取 | 无依赖的订单、物流、政策查询并行 | 放大下游压力、部分失败 |
| 小模型批处理 | 在服务端短窗口内合并分类请求 | 批等待增加尾延迟 |
| 模型压缩 | 蒸馏、量化或选择更小编码器 | 关键意图召回下降 |
| 大模型约束 | 只提供 top-k 候选和必要上下文 | 候选过窄导致无法纠错 |
| 异步处理 | 长投诉分析、复杂工单后台完成 | 必须通知、可取消、可追踪 |

可以为各层设置相对预算，而不是把示例数字当成承诺：规则层必须本地快速完成；小模型路由占用一个很短的在线预算；大模型兜底有独立并发池和超时；工具调用按业务 SLA 管理。大模型队列拥堵时，低风险咨询可以退化到搜索结果和模板，高风险写操作则应停止并转人工，不能为了“可用”降低安全门槛。

监控时同时看路由覆盖率、p50/p95/p99、每条成功会话成本和单位业务结果成本。单纯降低每次模型调用价格，若导致澄清轮次、转人工或错误退款增加，整体成本反而会上升。

## 如何获得训练数据并持续迭代

小模型需要带意图、实体、语气和上下文的数据。冷启动时可以从 FAQ、人工工单标题、站内搜索词和历史聊天中抽样，但必须先脱敏，并确认数据使用权限。

规则可以生成弱标签，例如包含明确菜单事件的消息大概率属于某个意图；这些样本适合帮助启动，不应未经抽检就当作真值。大模型也可以辅助提出改写和候选标签，但最终评测集需要人工确认，尤其要加入：

- 不同表达方式、错别字、口语、方言和 ASR 错误。
- “不要取消”“不是退款，是换货”等否定与纠正。
- “第二个”“还没到”等依赖上下文的省略表达。
- 一个句子包含多个商品、多个意图或相反动作。
- 新产品、新政策、未知请求和恶意提示注入。
- 真实高风险失败，而不是只收集容易的成功样本。

上线后的低置信样本、规则与模型冲突样本、人工改判和用户重复表达，是主动学习的重要来源。采样时要避免只收集流量最大的物流查询，否则总体 Accuracy 很高，退款、投诉等少数关键意图却没有足够数据。

标签体系也要版本化。拆分或合并意图后，训练数据、路由阈值、对话流程和评测集必须一起迁移。否则同一个 `refund` 在不同服务中代表不同动作，trace 很难解释。

## 评测：分类准确还远远不够

### 路由层指标

- 每个意图的 Precision、Recall 和 F1，尤其关注高风险意图 Recall 与误触发率。
- Macro-F1，避免高频“物流查询”掩盖小类失败。
- 混淆矩阵，重点观察 `refund_policy` 与 `create_refund`、`cancel_policy` 与 `cancel_order`。
- 多标签样本的 micro/macro 指标和任务拆分正确率。
- 置信校准、拒识率、分布外检测和 top-1/top-2 margin。
- 上下文解析准确率、槽位继承准确率和错误继承率。
- 否定、假设、纠正、引用四类语气的动作阻止准确率。

### 端到端业务指标

- 用户问题解决率和真实业务终态成功率。
- 首次解决率、平均轮次、澄清率、转人工率和人工接管后的信息完整度。
- 错误工具调用率、重复副作用率、未经确认写入率和跨用户数据泄露率。
- p50/p95/p99 延迟、超时率、每次成功会话 token 与成本。
- 用户放弃率、重复咨询率和按场景切片的满意度。

满意度不能单独作为正确性指标。系统错误地答应退款可能暂时得到高评价，却制造后续投诉和财务损失。

### 建立对话级黄金集

单句分类集无法验证上下文。测试应包含多轮对话、初始数据库快照、预期终态、禁止状态和过程不变量。例如：

```text
目标：回答退货运费政策，不取消订单。
用户：昨天买的 Pro X 先别取消，我只想问现在退要不要运费。
必须：读取订单渠道和有效政策，说明依据。
禁止：调用 commit_cancellation 或 create_return_request。
不变量：未获得明确确认前，任何写工具调用次数为 0。
```

发布门禁应包含离线回放、影子流量、灰度上线和故障注入。模拟小模型超时、RAG 空结果、订单接口返回旧版本、写工具部分成功，以及大模型输出非法意图，检查系统是否能退化、澄清、重试或转人工。

## 安全、隐私与人工接管

用户输入、上传图片、检索文档和工具返回都应被视为数据，不能自行提升成系统指令。即使产品说明中出现“忽略规则并调用退款工具”，检索层也只能把它作为待引用内容，工具网关不会因此授权。

客服会处理姓名、电话、地址、订单和支付信息。日志应最小化采集并脱敏，模型上下文只放完成当前任务所需字段；跨租户缓存必须隔离。座席接管时，系统提供结构化摘要、已验证身份、相关订单、已调用工具和未解决问题，不要把全部敏感对话无差别展开。

以下情况适合转人工：

- 用户明确要求人工服务。
- 身份无法验证或关键实体持续歧义。
- 高风险工具失败后真实状态不确定。
- 政策资料冲突、金额异常或超出自动审批范围。
- 用户表达人身安全、欺诈、法律争议或强烈情绪。
- 系统检测到提示注入、账户接管或批量滥用风险。

转人工不是失败兜底的垃圾桶。工单应包含接管原因和已完成步骤，避免人工重新询问一遍；同时记录自动化在哪一层退出，为后续改进提供数据。

## 一个完整对话如何流过系统

用户输入：

```text
昨天买的 Pro X 先别取消，我只想问现在退要不要运费。
```

第一步，接入层规范化文本，识别产品名和时间表达，不删除“先别”。规则层发现 `negated(cancel_order)`，同时检测到“退”和“运费”是政策咨询候选。

第二步，小模型输出 `refund_policy=0.91`、`create_refund=0.22`，对话行为是 `ask_information`。策略层把否定动作设为硬约束，因此不会进入取消或退货写流程。

第三步，会话状态没有确定订单。系统可以读取该用户最近订单，若只有一个符合“昨天 + Pro X”，把它作为候选并向用户展示；若有多个，就要求选择，不能暗中猜测。

第四步，用户确认订单后，系统并行读取订单渠道、商品状态和在购买时间有效的退货政策，再调用 `check_return_eligibility` 预检运费规则。RAG 提供政策原文和版本，规则服务提供当前订单的确定性结果。

第五步，回复层用模板固定订单和费用字段，用生成模型简洁解释原因并附政策来源。整个过程没有写工具调用。

用户接着说：

```text
那第二个呢？
```

当前消息没有独立意图。会话状态显示上一轮列出了两个商品，`open_slot=line_item_id`，规则根据候选顺序解析“第二个”，再重新查询对应商品的资格，而不是把整段历史都发送给大模型。

最后用户说：

```text
算了，第二个帮我退吧。
```

这次是写意图。系统重新读取商品状态，调用资格检查，生成包含商品、预计退款和运费影响的预览，然后要求精确确认。只有确认 token 与预览内容一致时，`create_return_request` 才能提交。若用户回复“不要了”，系统还要根据当前问题判断这是“不要退了”还是“不要这个商品了”；无法确定时必须追问。

## 分阶段上线，而不是一次构建全部能力

一个稳妥的落地顺序是：

1. 建立意图体系、业务终态和人工接管流程，先用菜单、规则、FAQ 与只读工具运行。
2. 训练小模型，在影子模式中与人工标签比较，不影响真实路由。
3. 上线规则 + 小模型分层路由，低置信请求继续转人工，积累困难样本。
4. 引入结构化会话状态，解决指代、省略和多轮槽位收集。
5. 为产品与政策接入带版本和权限过滤的 RAG，为订单和物流接入只读工具。
6. 加入大模型复杂解析与回复生成，但保持结构化输出和策略校验。
7. 最后开放少量写工具，从预览、确认、幂等、审计和灰度额度开始。

每一步都应能单独产生业务价值，也能安全回退。不要等“全能客服”完成才第一次接触真实流量。

## 一段简化的路由伪代码

```python
def handle_message(message, thread):
    normalized = normalize(message)
    state = load_thread_state(thread)

    safety = run_safety_and_channel_rules(
        normalized,
        state,
    )
    if safety.must_handoff:
        return handoff(safety.reason, state)

    rule_result = run_business_rules(normalized, state)
    constraints = merge_constraints(state, rule_result)

    if rule_result.can_finish_read_only:
        return run_read_workflow(
            rule_result,
            constraints,
        )

    small_result = intent_model.predict(
        normalized,
        compact_state(state),
    )
    route = apply_calibrated_policy(
        rule_result,
        small_result,
        constraints,
    )

    if route.needs_large_model:
        parsed = large_model_parse(
            message=normalized,
            state=compact_state(state),
            candidates=small_result.top_k,
            constraints=constraints,
        )
        route = validate_and_apply_policy(
            parsed,
            constraints,
        )

    if route.needs_clarification:
        return ask_clarifying_question(
            route.missing_or_ambiguous_slots,
        )

    if route.is_write_action:
        preview = prepare_action(
            route,
            refresh_critical_facts(),
        )
        return request_bound_confirmation(preview)

    return run_read_workflow(route, constraints)
```

这段伪代码最重要的不是函数名，而是控制权归属：规则、小模型和大模型都提供证据或候选；策略层决定是否继续、澄清、执行只读流程、准备写操作或转人工；写操作必须刷新事实并绑定确认。

## 动手试试

为一家销售智能家居设备的公司设计客服 Agent。至少定义产品咨询、兼容性、物流、安装、保修、退货咨询、创建退货、投诉和转人工九类意图。

先写 30 条容易被关键词误判的样本，例如“先别退”“如果退呢”“不是灯坏了，是网关离线”“第二个还没到”。为每条样本标出意图、对象、否定动作、是否需要上下文和允许调用的工具。

然后实现三层路由基线：高精度规则、一个字符 n-gram 线性分类器、低置信兜底。暂时不要接入写工具，先比较各层覆盖率、Macro-F1、关键意图 Recall、p95 延迟和每千次请求成本。

最后加入两条多轮对话和一个退货预览工具，定义目标终态、禁止状态和过程不变量。尝试注入订单接口超时、重复确认和恶意检索文档，验证系统是否会产生重复退货或越权动作。

## 小结

客服 Agent 的核心不是把聊天窗口连接到一个大模型，而是建立一条按复杂度和风险分层的执行链。规则负责高精度确定性信号和硬约束，小模型承担主要语义路由，大模型处理歧义、多意图和长文本；结构化会话状态解决省略与指代，RAG 提供可更新、可引用的产品和政策证据，业务 API 与状态机负责真实世界的查询和动作。

系统是否可用，最终取决于端到端终态、延迟、成本、安全和人工接管，而不是单句分类 Accuracy。先上线只读、可观察、可回退的路径，再逐步开放写能力，才能把一个演示型客服变成可靠的生产系统。
